## 1. 测试目标与方法

### 1.1 目标

找出**能让 CatOS 内核 panic、死机、挂起、重启、或内核态数据被破坏的输入**。不是功能回归，是对抗性破坏：红队以"击溃它"为目标，蓝队只堵**已复现**的洞。

### 1.2 被测对象假设（决定定级方式，来自 `tests/isolation_logs/SEV-FRAMEWORK.md §1`）

| #  | 事实                                                      | 依据                                |
| -- | ------------------------------------------------------- | --------------------------------- |
| S1 | 单用户、单控制台（VGA 文本 + PS/2），无 SSH/串口 getty/第二会话             | 驱动只有 `-display none` + HMP        |
| S2 | **shell 就是控制台循环，且无人重生它**；TID 0 变 `T_UNUSED` 后没有任何东西会重启它 | `task.c:385-392` 注释原文             |
| S3 | `run` 即 root：shell 派生的每个 CE 都继承 `UID_ROOT`              | 同上                                |
| S4 | 无网络（guest 内 `net_ready=0`、内核枚举无 NIC）                    | `isolation_logs/SUMMARY.md` D3/D4 |
| S5 | 磁盘写入会持久化（写坏的是那份 raw 副本）                                 | 同上 C 项 sha256 变化                  |

由 S1–S3 得到一条与 Linux 直觉相反的推论：**"只是把 shell 杀了"在本系统里等于整机报废**（无 getty、无 respawn、无第二入口），因此此类现象**不得**按"单任务影响"降级（`SEV-FRAMEWORK.md` W5/W6）。

### 1.3 方法

- **驱动**：`tests/crash_attack.py`（每个攻击一个全新 guest，`-net none`、`-display none`、私有 HMP 端口 `:4492`、每次一份独立 64 MiB 磁盘副本）。
- **判定**（与红队日志完全一致的术语）：
  | 判定            | 含义                                                                                             |
  | ------------- | ---------------------------------------------------------------------------------------------- |
  | `C1 PANIC`    | `KERNEL PANIC`，或 ring0 异常路径停机（`ring0 kernel fault - system halted`），且 CPU 卡在 IF=0 的 cli/hlt 循环 |
  | `C2 REBOOT`   | guest 复位（`-no-reboot` 下 QEMU 退出），或 GRUB 画面回来                                                   |
  | `C3 HANG`     | 什么都不应答：无 `ATK-DONE`、`faultinfo` 无输出，但 monitor 仍能读屏                                             |
  | `C4 FAULT-R0` | `faultinfo` 报 ring0 取异常而内核存活                                                                   |
  | `C5 CORRUPT`  | 攻击结束（或静默死亡）但控制台/系统不再正常工作                                                                       |
  | `OK`          | 内核继续服务：攻击返回，或攻击者被自己的 ring3 异常杀死                                                                |
- **活性探针**（区分"攻击者死了"与"整机死了"）：攻击后向 guest 键入 `faultinfo`，要求屏幕上出现 `last fault` / `no fault recorded since boot`；同时做 4 次 `info registers` 采样，用 `EIP` 抖动窗口 + `EFL.IF` 区分"ring0 忙等"（IF=0，冻结）与"idle 循环"（IF=1，`sti; hlt`）。
- **判定实现**：`tests/crash_attack.py:280-353`（活性探针与 `stuck` 判定）、`:172-192`（致命串/重启用轮询）。

### 1.4 两个必须先知道的内核事实（贯穿全文）

1. **`panic()` 是死代码**。定义在 `src/diag.c:83`（打印 `*** KERNEL PANIC: ... ***` 后 `cli` + `hlt` 死循环），全仓**零调用点**（`grep -rn "panic(" src/ include/` 只命中定义 `diag.c:83` 与声明 `include/diag.h:24`）。  
   → **"KERNEL PANIC" 永远不会出现在屏幕上**。任何"看到 panic"的描述都是错误转述；真实击溃标志只有 `ring0 kernel fault - system halted`，或者更常见的——**什么都不打印，直接挂死**。
2. **`int 0x80` 是 0xEE 门，`IF=0`，不可抢占**。`src/intr.c:223`：`idt_set(0x80, (uint32_t)isr_stub_table[48], 0xEE);`（0xEE = present + DPL3 + **interrupt gate**）。  
   → **syscall 内部一旦死循环，时钟中断进不来，就没有任何东西能把它抢回来**。这条事实是 A04 / A08 / A09 三条结论的物理基础，也是把"一个死循环"从 `SEV4` 抬到整机级的原因。

### 2.3 合规性措辞（必须照此引用，不要升级承诺）

> 本轮**保证**的是：guest 侧没有网络、没有共享目录、没有端口转发、没有音频后端，且没有已知的逃逸通道；磁盘是副本；收场只按 PID。  
> 本轮**不能**保证"不影响外界"。该承诺成立有一个消不掉的前提：**QEMU 本身不存在可被 guest 利用的漏洞（0day 或未修的已知 CVE）**。  
> 因此正确表述是"**在上述前提下**，本轮不影响外界"，**不是**"我们保证了不影响外界"。这个差别不是抠字眼——R1 是 `RESIDUAL-RISK.md` 里明确标为"**高**"的残余风险。

**`-net none` 的证据强度（不是 grep 出来的）**：四条**独立互证**，任一条单独都不够——  
① 拦截 `boot()` 的 `subprocess.Popen` 拿到构造出的真实 argv；② QEMU 起来后读该 PID 的 `Win32_Process.CommandLine`（确认运行时而非源码声明）；③ guest 内核**自己枚举**的 PCI 表里没有 NIC；④ guest 内 `net_up()==0` / `netinfo` 报 `no network card found`。见 2.1 的 A1 / D1 / D3 / D4。

**monitor 端口的正确表述**：`tcp:127.0.0.1:4494` 绑回环，**guest 够不到**（无网卡）；但**宿主上任何本地进程都能连、且 HMP 无认证**——这是**残余风险 R2**，不是"隔离缺陷"，更不能写成"存在远程可利用的监控端口"。

### 7.3 为什么"只看 ATK-DONE"是不够的（方法论，已可用）

`K1` 的 baseline **也会打印 `ATK-DONE`**——攻击在摧毁 shell 之后继续运行。所以判据必须是"**攻击之后 shell 还能不能应答命令**"，永远不能是"有没有 ATK-DONE"。  
`regression_after_fix.py` 的活性探针做法可复用：攻击后键入 `faultinfo`，要求屏上出现 `last fault` / `fault recorded`（全新 guest 不可能事先含这串文本，因此能排除 80×25 VGA 陈旧画面的陷阱）；`K1` 额外跑 `/bin/hello.ce`。

#### 10.5-9 `A14` 的 `STEP 3/4` 揭示了"vsyscall thunk 页对 ring3 可写"（值得单独跟进的设计问题）

`A14-stack-rec.txt:22-24`：

```
STEP 3: -- vsyscall page is user-writable: peek at the thunks
thunk[0]=0x02080000 api ptr=0x02080800
STEP 4: -- self-modify a vsyscall thunk (ring3-only capability?)
patched=235 restored
```

含义：CE 能**读并写**内核为它生成的 `int 0x80` thunk 页（攻击者把某字节改成 235 后又改回），且改完之后 syscall 仍按预期工作。  
**为什么这不算"提权"，但必须记录**：

- 不构成越权——CE 本来就能自己发 `int 0x80` 并任意设置寄存器，改 thunk 只是换一种写法，收益为 0；
- **但它说明内核把"syscall 入口代码"写进了用户可写页**。如果将来有任何设计**信任 thunk 的内容**（例如内核读回 thunk 校验、或 thunk 里藏了内核写入的数据），这就变成可被 ring3 篡改的信任根。
- **建议**：由 code-reviewer 确认这是预期设计（thunk 在用户页是实现简单性的取舍），并**明确写进架构文档**；若无意如此，考虑把 thunk 页设为只读（`mkdir` 到页表只读位）。

  |  |  |  |  
  | --- | --- | --- |
