# 隔离边界的残余风险（Residual Risk）— CatOS 崩溃攻击对抗测试

> 本文件是 `tests/isolation_verify.py` 的配套说明：脚本证明"四条隔离真实成立"，
> 本文件诚实列出"四条隔离**没有**覆盖到什么"。核验结论 10/10 PASS 不等于零风险。

核验环境（2026-11-13，`tests/isolation_logs/R_residual_risk.txt` 为原始输出）：

| 项 | 值 |
|---|---|
| QEMU | `C:\qemu-portable\qemu-system-i386.exe`，**11.1.0** (v11.1.0-12130-ge470268ff4) |
| 运行身份 | `杨氏\Admin`，完整性级别 **Medium**，`IsInRole Administrator = False`（**未提权**） |
| `-sandbox` | **不可用**：`There is no option group 'sandbox'`（Windows 构建未编译 seccomp 沙箱） |
| 宿主并发 guest | 至少 2 个（红队 `:4492`；`D:/CatOs` 的 svga24 回归 `:4467`） |

---

## R1（高）QEMU 是唯一的安全边界

guest 内是故意写坏的恶意 CE 程序。它能碰到宿主的**唯一**路径是 QEMU 的设备模拟代码。
本轮已把攻击面压到最小（无网卡、无共享目录、无音频后端、磁盘是副本），但剩下的
设备仍然全部在 guest 的可控输入范围内：

- VGA（`1234:1111` std VGA）、IDE/PIIX3、PS/2 键盘控制器、ACPI（`8086:7113`）

这些正是历史上 CVE 密集的区域。QEMU 11.1.0 是较新版本，**降低了**已知漏洞命中的概率，
但"没有已知漏洞"和"不会被打穿"不是一回事。

**降低建议**：① 保持 QEMU 版本更新（这是最有效的一条）；② 以**非特权用户**运行
（已核实：Medium 完整性、非管理员组，攻击成功也只能拿到普通用户权限）；③ 不添加
任何 `-device`（尤其音频、USB、网络）——本轮 `crash_attack.py` 与 `isolation_verify.py`
都没有加；④ 攻击窗口短（本脚本单 guest ≈ 40 s 后即退出）。

## R2（中）HMP monitor 端口是宿主机上的无认证通道

`-monitor tcp:127.0.0.1:4494,server,nowait` 只绑回环，guest **够不到**
（guest 无网卡，见 D2/D3/D4 证据）。但**宿主上任何本地进程**都能连上去，且 HMP
**没有认证**。连上后可用的命令里包括能写宿主文件的：

- `pmemsave <addr> <size> <hostpath>`、`screendump <hostpath>` —— 写任意宿主路径（以当前用户权限）
- `drive_add`、`migrate`、`quit`

这不是 guest 逃逸（guest 到不了这个端口），而是"monitor 端口本身是一个宿主侧特权通道"。
同一台机器上还有别的 driver 在使用 4444/4460/4467/4468/4492。

**降低建议**：① 一个 driver 一个端口（已在做）；② 端口只绑 `127.0.0.1`，永不 `0.0.0.0`
（已在做，脚本对 LOCAL 地址列做断言）；③ 核验/攻击结束后立刻 `kill_qemu(proc)`，
不要留长驻 monitor；④ 若要更严，QEMU 支持 `-monitor stdio`（无端口）或将端口随机化。

## R3（中）同宿主多 guest 并发，安全边界是共享的

核验时宿主上至少同时有 2 个其它 guest。它们与本轮的 guest **共享同一个 QEMU 二进制、
同一个用户令牌、同一个内核**。因此：

- 任何一个 guest 打穿 QEMU，落地的权限与位置都一样——"我们这轮很小心"不能保护宿主；
- 反方向也有影响：**我的核验 guest 会抢 CPU**，可能让红队基于时间的高级判据（C3 HANG 的
  25 s 判定）产生偏差。本次核验只启动 1 个 guest、约 40 s 即退出，影响可忽略但非零。

**降低建议**：跑时序敏感的崩溃判据（C3 HANG / 抢占相关）时，宿主上不要并发跑其它 guest；
若必须并发，`uptime`/`ps` 之外还要看宿主侧 CPU 占用（`Get-Process qemu*`）。

## R4（中）显存/内存类 DoS 会穿透进程边界打到宿主

QEMU 进程只受 `-m 256` 限制（已加，防止 guest 膨胀）。但没有 cgroup/Job Object 级别的
CPU 与内存硬限额，所以一个**死循环**攻击会让 QEMU 进程吃满一个核心，直到 driver 超时
把它杀掉。这属于"宿主被拖慢"，不是"宿主被攻破"，但同样是"影响外界"的一种。

**降低建议**：① 每个攻击都带超时并用 PID 收尾（红队已按此实现）；② 若要硬限，可用
Windows Job Object（`JOB_OBJECT_LIMIT_PROCESS_MEMORY` / CPU rate control）包住 QEMU；
③ 同时最多一个攻击 guest。

## R5（低，但需知会）**测试基础设施自身的攻击面**：音频后端 / screendump 是 guest 可控数据落盘通道

> 这条不是 CatOS 的缺陷，是**我们这套测试工具**的攻击面，报告里要单列一条，
> 不要混进"内核问题清单"。

`tests/snd_regress.py` 使用 `-audiodev wav,id=snd0,path=<宿主路径>`。这类后端会让
**guest 产生的音频数据**以宿主文件形式落地，体积由 guest 播放时长决定（磁盘 DoS 面），
内容也由 guest 控制。本轮 `crash_attack.py` **没有**启用音频后端，所以当前不构成风险；
但如果后续为"音频子系统崩溃"加设备，请把它当作一条 guest→host 数据通道来评估。

**降低建议**：本轮不要给攻击 guest 加 `-audiodev`/`-device sb16`；若必须测音频，
把 `path=` 指向一个专用目录并用配额限制。

## R6（低）git 分支隔离是逻辑隔离，不是文件系统隔离

三个 worktree（`D:/CatOs`、`master-a125998e`、`redteam-crash-2026-11-13`）**共享同一个
`.git` 目录**。分支隔离保证"我们的提交落在自己的分支上"，但保证不了"某人手滑
`git checkout` 或直接改文件"——那需要纪律和 review，不是脚本能证明的。
核验证据只覆盖到：本 worktree 在 `redteam/crash-attack-2026-11-13`、主工作区
`master-a125998e` 的 `git status --porcelain` 为空（未被我们污染）。

**降低建议**：本轮禁止 git 写操作（brief 已写明）；收尾时用 `git -C <worktree> status`
复核三处，再由主理人决定合并。

## R7（低，但会污染测量）**宿主只有 4 个物理核**，并发 guest 会让"卡住"类判定不可比

实测（`Win32_Processor`）：**Intel i3-12100，`NumberOfCores = 4`，`NumberOfLogicalProcessors = 8`**
（4 核 8 线程 SMT）。`nproc` / `/proc/cpuinfo` 报 **8** —— 那是**逻辑**处理器数，不是 8 个独立核。
团队里流传的"nproc=16"**不成立**，实际是 **8 逻辑 / 4 物理**。

为什么这条要写进残余风险，而不是当成环境噪声：

- QEMU 的 TCG 是**纯软件模拟**，每个 guest 都要吃掉真实 CPU 时间；
- 本轮最多同时跑过 **4 个 guest**（红队 `:4492`、蓝队 `:4496`、我 `:4494`、外部会话 `:4467`）；
- 4 个 guest 抢 4 个物理核 + SMT = **毫无余量**，宿主自身的编译/杀毒/构建还会插进来；
- 后果很具体：**"25 s 内没有 `ATK-DONE`" 这类墙钟判据在高负载下会误判为 HANG**，
  同一攻击在低负载下可能"看起来正常"。所以 **C3（HANG）的复现率在不同并发度下不可比**。

**这不是内核缺陷，因此不列任何 SEV**；它只影响两件事：
1. `SEV-FRAMEWORK.md` 的 W3（竞态折扣）适用条件——凡判 C3 必须附"当时宿主上有几个 `qemu-system-i386.exe`"；
2. 报告里"复现率 n/m"的**可比性**——不同轮次并发度不同，n/m 不能跨轮直接比较。

**降低建议**：关键攻击（尤其 C3 类）串行执行，同一时刻只允许 1 个 guest；必须并发时，
在日志里记下并发度与当时 `%CPU`，供事后判断该轮 n/m 是否可信。

## 一句话结论

在**当前这台机器、当前这个 QEMU 版本、当前这套启动参数**下，网络/磁盘/工作目录/进程
四条隔离都有可核查证据、全部成立。

但要严格区分我们**保证**了什么、**依赖**了什么：

- 我们保证的是：**guest 侧没有网络、没有共享目录、没有端口转发、没有音频后端，
  且没有已知的逃逸通道；磁盘是副本；收场只按 PID**。
- 我们**不能**保证"不影响外界"。这个承诺成立有一个我们消不掉的前提条件：
  **QEMU 本身不存在可被 guest 利用的漏洞（0day 或未修的已知 CVE）**。
  剩余设备面（VGA/IDE/PS2/ACPI）恰是 QEMU 历史 CVE 密集区，这不是靠我们的参数能消除的。

所以报告里的措辞必须是"**在上述前提下**，本轮不影响外界"，而不是"我们保证了不影响外界"。
其余 R2–R6 都有明确的降低措施。
