# CatOS 崩溃攻击 —— SEV 定级框架（v1.1）

> 用途：把红队战果**机械地**映射成一个级别，避免"谁喊得响谁严重"。
> 本文只定尺子，不定案。战果一到，直接填第 8 节的表。
> 定级依据是**被测工件（`catos.iso` + `catos_disk.img`）的实际行为**，不是工作区源码。
> 源码里已经修好、但 ISO 没重建，对定级毫无意义——这一条请所有人守住。

**v0.2 变更**：把 SEV1 拆成 **SEV1-a / SEV1-b** 两种恢复成本（team-lead 2026-11-13 评审意见）。
两者级别相同，但**值班动作完全不同**，不许混为一谈。见第 3.1 节。

## 1. 系统假设（定级的前提，来自实际观测，不是推测）

| # | 事实 | 证据来源 |
|---|---|---|
| S1 | **单用户、单控制台**：VGA 文本 + PS/2 键盘，无 SSH、无串口 getty、无第二会话 | `qemu_driver` 只有 `-display none` + HMP `sendkey`/`screendump` 这一条交互路径 |
| S2 | **shell 就是控制台循环，且无人重生它**：TID 0 = `shell_run()`（`kernel.c:98` 唯一一次调用，永不返回）；该槽位一旦 `T_UNUSED`，全树没有任何"发现 T_UNUSED 就重生 shell"的逻辑 | **代码级**（已自查，不引注释）：`task_cleanup()` `task.c:332-345` 只释放用户地址空间/VMA/pipe/console 归属权，**完全不改 `state`**；`task_kill()` `task.c:404-414` 是 `task_cleanup()`(**405**) → `exit_code=-9`(**406**) → `state=T_ZOMBIE`(**407**) → `maybe_autoreap()`(**409**) → `w("[kill: tid …]")`(**413**) → `return 0`(**414**)，即**打印在所有破坏性动作之后**；`maybe_autoreap()` `task.c:349-352`：`if (!t->parent \|\| t->parent->state != T_WAIT_CHILD) t->state = T_UNUSED;` —— **shell 没有 parent，直接置 T_UNUSED，连僵尸都不留** |
| S3 | **`run` 即 root**：shell 派生的每个 CE 都继承 `UID_ROOT` | `task.c:402-403` 的 uid 门是 `by_uid != UID_ROOT && t->uid != by_uid && !(caps & CAP_KILL)`，而 `by_uid` 恒为 root → 该门对"杀 shell"从不生效；另见 `task.c:385-392` 注释（仅作旁证） |
| S4 | **无网络**：guest 内 `net_ready=0`、内核枚举无 NIC | 我 2026-11-13 隔离核验 D3/D4（`isolation_logs/D_*.txt`） |
| S5 | **磁盘写入会持久化**：写坏的是那份 raw 镜像，重启后依然是坏的（除非重拷副本） | 隔离核验 C 项：guest `touch` 后副本 sha256 改变 |
| S6 | **无看门狗、无自动重启**：`boot()` 传 `-no-reboot`，guest panic = QEMU 退出 | `qemu_driver.boot()` argv（A1 项） |
| S7 | **宿主侧可观测**：guest 挂了，QEMU 进程/镜像文件仍在，可事后取证 | 隔离核验 C/D 项 |

由此得到三条与 Linux 直觉相反的推论：

- **推论 A（最重要）**：`killing the shell` 不是"杀掉一个进程"，而是**整机报废**。
  没有 getty、没有 respawn、没有第二个入口 → 用户除了 `system_reset` 别无选择。
  在 Linux 上这是"某用户把自己 shell 搞没了"，在这里是 **SEV1 级整机不可用**。
- **推论 B**：**"需要 root"在本系统里不构成降级理由**。任何 `run xxx.ce` 都是 root；
  而"运行别人给的 .ce"正是这个系统的正常用法（不是罕见的高权限操作）。
  所以**默认把 `run` 视为默认可达**，攻击者模型 = "能让用户运行一个程序的任何人"。
- **推论 C**：**能持久化破坏镜像的攻击 > 一次性 panic**。前者恢复成本是"重拷镜像 + 丢用户数据"，
  后者是"重启 70 s"。严重性必须区分这两者（见第 4 节加权）。

## 2. 定级前必须先落地的 3 个事实（否则不许定级）

| 待确认 | 怎么确认 | 影响哪个分叉 |
|---|---|---|
| **F1 控制台能否恢复？** 攻击后键盘还有响应吗？能重新拿到 prompt 吗？还是只能 `system_reset`？ | 攻击后：① 敲回车看有无回显；② HMP `sendkey ret` 后 `screendump` 看屏幕是否变化；③ HMP `info registers` 看 CPU 是否还在跑（在跑≠shell 在） | SEV1 与 SEV2/3 的**主分叉** |
| **F2 镜像是否被持久破坏？** 干净退出后重启，坏状态还在吗？ | `quit` 干净退出 → 重算副本 sha256（对比攻击前）→ 再用同一副本重启一次看是否复现 | 决定是否 +1 级 |
| **F3 有没有跨出 guest？** QEMU 进程是否异常退出？宿主文件是否被改？（正常攻击**不应**发生） | 攻击前后：QEMU PID 存活、`catos_disk.img` sha256、宿主 `%TEMP%`/worktree 关键文件 hash | 一旦成立 → 直接 SEV1，不看其它 |

## 3. SEV1–4 判据

### SEV1 —— 整机报废 / 跨出边界

**判据（满足任一）**
1. 控制台永久丢失：prompt 不再回来，**且**无任何恢复路径（F1 = 不可恢复）；
2. guest 侧 QEMU 进程异常退出/异常终止（`-no-reboot` 下 panic 后 QEMU 退出也属此类）；
3. **任何 guest→host 影响**（宿主文件被写、QEMU crash、monitor 端口被 guest 触达）。

**标准答案模板**
- 影响面：整机（全部用户=那一个人；直到人工 `system_reset` 或重启 QEMU）
- 需 root：**不评估**——`run` 即 root，见推论 B
- 需恶意文件投递：**是**（无网络 S4），但这是本系统的正常用法，不降级
- 恢复手段：宿主侧 `system_reset` / 重启 QEMU（≈70 s）；若镜像同时被写坏 → 重拷 base 副本
- 触发前提：任意用户 `run <任意 .ce>`，无额外前置条件

### 3.1 SEV1 的两个子型：恢复成本不同，值班动作不同

**同一个 SEV1，两种完全不同的后果。值班的人必须先分清是哪一个，否则会用错恢复手段。**

| | **SEV1-a：控制台丢失，镜像完好** | **SEV1-b：镜像被写坏，重启回不来** |
|---|---|---|
| 现象 | prompt 再也不回来；键盘无响应或只回显不执行；**但 QEMU 进程还活着，磁盘仍可读** | 同上，且**重启后依然坏**（甚至启动不了） |
| 根因 | shell（TID 0 = 控制台循环）死掉且无人重生（S2）；`-no-reboot`（S6） | 攻击写坏了 FAT32 元数据/引导区/关键文件（S5 持久化） |
| **恢复动作** | **`kill_qemu` → 重启 QEMU**（或 HMP `system_reset`）；**镜像不用动** | **回滚镜像**：从 `kernel_v25/catos_disk.img` 重拷一份副本；重启是**无效**的 |
| 数据损失 | 内存态丢失（未落盘的编辑内容），`/` 上的文件**保留** | `/` 上的用户数据**丢失**（回到上一次干净副本） |
| 恢复耗时 | ≈70 s（一次 boot） | 重拷 64 MB + 一次 boot，且**攻击者的写入无法追溯恢复** |
| 值班第一步 | `system_reset`，然后看 prompt 是否回来 | **先别重置**：先 `sha256` 比对副本与 base，留证；再回滚 |
| 取证要求 | 屏幕文本 + `info registers`（确认 CPU 还在跑） | 攻击前后 sha256 + 坏在哪个扇区/文件（供复盘） |

**判定方法**：攻击后先 `quit` 干净退出、再重启一次——
- 重启后正常 → SEV1-a（顺手记下"仅内存态丢失"）；
- 重启后仍坏/启动失败 → SEV1-b（**+W1 加权已包含在 SEV1 内，不再升级，但必须按 b 处置**）。

> ### ⚠️ 命名纪律（v0.5 新增，已发生过一次误用）
> **`a` / `b` 只表示"恢复成本"，绝不表示"第几条 bug"。**
> 判断依据是 **F2（重启后是否仍坏）**，与根因是 `task_kill` 还是 `be_vbe24` **无关**。
>
> - ✅ 正确：两个**完全不同**的根因（一个在 `task_kill`、一个在图形后端算术），
>   只要都没写坏镜像 → **都是 SEV1-a**，是两条**独立 finding**（V-01、V-03）。
> - ❌ 错误：把"A10 是另一个 bug"说成 "SEV1-b"。值班工程师看到 `b` 会去**回滚镜像**，
>   而实际上只要重启就能恢复——这会让人做多余的破坏性操作。
>
> finding 之间靠**编号**（V-01/V-02/V-03）区分，不靠子型字母。

> 这正是 F1（控制台能否恢复）与 F2（镜像是否持久破坏）必须**分开问**的原因：
> F1 决定"是不是 SEV1"，F2 决定"是 a 还是 b、值班该重启还是该回滚"。

### 3.2 定级的前置条件：工件身份必须成对出现（`SIDE=BEFORE` / `SIDE=AFTER`）

同一条攻击的结论**必须同时给出修复前与修复后两个工件的 hash**，否则视为未验证。

| 标记 | 含义 | 当前工件 |
|---|---|---|
| `SIDE=BEFORE` | 修复动作落盘**之前**构建的工件，用于证明缺陷存在 | `ISO=4dc87877beb6ac53…`（17:51:55）+ `DISK=39296ad8…` |
| `SIDE=AFTER` | 最终权威构建产物，用于证明已修复 | 待蓝队构建（新 hash，我重跑核验后填入） |

- `SIDE=BEFORE` 的结论只能写成"**修复前该内核**……"，**不得**写成"当前内核的表现"。
- `tests/baseline-catos.iso` 与 `catos.iso` **字节完全相同**（`4dc87877…`，两边独立 sha256 复核一致），
  所以蓝队 baseline 侧的证据与"被测工件"是**同一个对象**，不需要额外排除"两台不同镜像"的可能。
- `tests/baseline-catos.iso` 是**冻结证据**，任何人不得覆盖。
- 报告里禁止出现"已修复（新 ISO）+ 仍可复现（旧 ISO）"混排而不标 hash。

**本系统给了我们一条不依赖推断的硬判据**（比"看 prompt 没了"强）：`task_kill()` 的
`w("[kill: tid …]")` 打印在**所有破坏性动作之后**（`task.c:413`，破坏动作在 405–409，
`return 0` 在 414）。

**但 BEFORE 侧不能把"屏幕出现这行"当必经条件**（code-reviewer 2026-11-13 提醒，采纳）：
80x25 屏，ATKPROC 杀完 shell 后还要打印几行，这行**可能被滚掉**，硬性要求会把一次有效实验判成
inconclusive。所以两侧的断言**不对称**：

| 侧 | 主判据（必需） | 辅判据（有则更强，无则不扣） |
|---|---|---|
| **BEFORE** `4dc87877` | **`alive=False`**（`faultinfo` 无回应）+ `kill(0)` 返回 `0` | 屏幕出现 `[kill: tid 0 (shell)]` |
| **AFTER** 新 hash | `kill(0)` 返回非 0（预期 `-2`）+ `alive=True` + `ATK-DONE` | —— 且**禁止**出现 `[kill: tid 0 (shell)]` |

**为什么 AFTER 侧的 forbid 不怕"滚屏导致漏判"**：若守卫缺失（未修复），`kill(0)` 会返回 `0`，
**先违反必需项**，所以"该行被滚掉 → forbid 误判通过"这条路走不到 PASS。
必需项与禁止项是**互锁**的，不是两条独立检查——这是 code-reviewer 的 K1 断言设计得对的地方。

### SEV2 —— 主功能降级 / 需人工介入才能恢复

**判据（满足任一）**
1. 能破坏关键子系统状态（文件系统元数据、中断控制器、调度器、控制台所有权），
   导致**后续正常操作全部失败**，但 `system_reset` 可恢复；
2. **可持久化破坏磁盘镜像**（F2 = 是）：重启后仍然坏；
3. 对内核对**合法输入**产生错误的最终结果（数据损坏、静默错误），不是崩溃；
4. panic / fault 可稳定复现，且每次都要人工重启（批量攻击场景下等于不可用）。

- 影响面：整机功能受损，重启可恢复（但若 S5 成立，重启不恢复 → 升 SEV1）
- 需 root：不评估（同上）
- 恢复手段：`system_reset`；镜像坏了要重拷副本 + 用户数据丢失
- 触发前提：`run <恶意 .ce>`；可能还需要特定时序/特定输入

### SEV3 —— 单任务影响 / 控制台存活

**判据（满足任一）**
1. 只杀死/挂死**自己的**进程，控制台仍可用、能重新 `run`；
2. 影响限于该任务的数据（进程内错误、返回值错误），不影响其它任务与内核状态；
3. 需要 root、需要投递恶意文件，但**代价仅是该任务失败**。

- 影响面：单任务
- 恢复手段：重新 `run`
- 触发前提：`run <恶意 .ce>`

### SEV4 —— 低影响 / 体验与提示问题

**判据**
1. 仅日志/提示/错误码不当；2. 仅非默认配置下成立（如自建 ISO 开了某个选项）；
3. 理论问题、无可用 PoC；4. 需要物理/调试器级别的介入。

- 影响面：无功能影响
- 恢复手段：无需
- 处理：登记，排期

## 4. 加权与升降级规则

| 规则 | 触发条件 | 调整 |
|---|---|---|
| W1 持久化加权 | F2=是（镜像被写坏，重启不恢复） | **+1 级**（SEV3→SEV2，SEV2→SEV1） |
| W2 跨边界 | F3=是（QEMU 异常退出 / 宿主文件被动 / guest 触达 monitor） | **直接 SEV1**，不看其它 |
| W3 竞态折扣 | 复现率 <50% 且依赖宿主负载/时序 | **−1 级**，但必须在报告里标注复现条件 |
| W4 批量折扣 | 单次攻击只影响一个任务，且**攻击者无法批量投递**（需用户逐个手工 run） | 不调整（本系统本来就是逐个 `run`，这不算罕见） |
| W5 **禁止折扣** | 「需要 root」 | **不得据此降级**（推论 B） |
| W6 **禁止折扣** | 「只影响控制台，不影响内核数据」 | **不得据此降级**，因为控制台=唯一入口（推论 A / S2） |

> W5/W6 是本框架最关键的两条。Linux 上的直觉在这里会给出错误答案：
> 「要 root 才能触发」→ 这里人人都是 root；「只是 shell 挂了」→ 这里 shell 挂了就没救了。

## 5. 定级决策树（按顺序问，命中即停）

```
Q1 有跨出 guest 的迹象吗？（QEMU 退出 / 宿主文件变 / monitor 被触达）
   └─ 是 → SEV1（W2）
Q2 控制台能否恢复？（F1）
   └─ 否（prompt 再也不回来，只能 reset） → SEV1，再看 Q2b 决定 a 还是 b
        Q2b 重启后是否仍坏？（F2）
            ├─ 否 → **SEV1-a**：`system_reset` / 重启 QEMU，镜像不动
            └─ 是 → **SEV1-b**：先留证（sha256 对比 base），再回滚镜像
Q3 镜像是否被持久破坏？（F2）
   └─ 是 → 至少 SEV2（W1 +1；若同时需要人工 reset 才算恢复 → SEV1）
Q4 是否需要重启才能继续正常操作？
   └─ 是 → SEV2
Q5 是否只影响自身任务，控制台存活？
   └─ 是 → SEV3
Q6 是否仅提示/日志/理论问题？
   └─ 是 → SEV4
Q7 都不符合 → 不是缺陷，是设计取舍（写进报告的"非缺陷"一节）
```

## 6. 响应节奏

| 级别 | 阻塞发布？ | 首次响应 | 缓解/修复窗口 | 回归门禁 | 对外口径 |
|---|---|---|---|---|---|
| **SEV1** | **是，立即冻结**（禁合并、禁发版、禁重建 ISO） | **立即**，全员响应（本次角色：指挥官=team-lead，技术定位=code-reviewer，复现与回归=testing-expert，定级与节奏=sre-engineer） | 24 h 内必须有缓解（禁用入口）或回滚；修复须附**自动化回归用例**。**处置按子型分流：SEV1-a → 重启即可恢复，先恢复再定位；SEV1-b → 先留证（sha256）再回滚镜像，别急着重启** | 必须：攻击脚本 + 断言入库，CI/回归门禁跑通才许发布 | 内部事故通告（现状/影响/下一步/时间点）；若属用户反馈轮，附带"在修复前不要运行不可信 .ce" |
| **SEV2** | **是** | 15 min | 当前迭代内 | 必须有回归用例 | 内部通报，进已知问题清单 |
| **SEV3** | 否（可带已知问题发布） | 1 h | 下个迭代 | 建议有 | 登记已知问题 |
| **SEV4** | 否 | 下个工作日 | 排期 | 不需要 | 记录 |

**状态更新节奏**：SEV1 每 30 min 一条，格式固定为"已知事实 / 已采取措施 / 下一步 / 下一次更新时间"，
不写猜测、不写情绪、不写"应该快好了"。SEV2 每 2 h 一条。SEV3/4 随工单。

**复盘**：SEV1/SEV2 结束后 48 h 内出无责复盘（时间线 / 5 Why / 行动项 + 负责人 + 截止日），
行动项必须**可验证**（"补一个用例"而不是"加强测试"）。

## 7. 定级所需输入清单（红队提交战果时请按此填）

每条攻击一行，缺项视为未定级（不许用"大概是 HANG"这种描述）：

| 字段 | 说明 |
|---|---|
| 攻击 ID / 名称 | 如 `A07`、`kill(0) 杀 shell` |
| 投递方式 | 怎么进到 guest 的？（`run` 一个 .ce？内建命令？） |
| 执行前提 | 是否需要特定权限、特定文件、特定时序 |
| 可观测现象 | **屏幕原文**（不是转述）、错误码、是否 panic |
| F1 控制台可否恢复 | 攻击后键盘有无响应 / 能否再拿 prompt（→ 决定**是不是** SEV1） |
| F2 镜像是否被破坏 | 攻击前后 sha256，**重启一次后是否仍复现**（→ 决定 SEV1-**a 还是 b**、值班重启还是回滚） |
| F3 宿主侧异常 | QEMU PID 是否存活、宿主有无文件变动 |
| 复现率 | n/m，以及当时的宿主负载（同时有几个 qemu） |
| 恢复方式 | 重新 `run` / `system_reset` / 重拷镜像 |

### 8.1.1 V-02 的 Q2 为什么是"代码级",不靠 C3 的 25 s 墙钟

红队把 A08/A09 判为 C3（无 `ATK-DONE` + `faultinfo` 无回应），而 C3 依赖墙钟——
在 4 个 TCG guest 抢 4 个物理核时（见 RESIDUAL-RISK R7）墙钟判据不可靠。但这条**不需要计时**：

```c
void task_wait_child(task_t *child) {                    /* task.c:417-421 */
    while (child->state == T_ZOMBIE || child->state == T_UNUSED ? 0 : 1)
        task_block(T_WAIT_CHILD);                        /* 只有"子进程死"才会唤醒 */
    child->state = T_UNUSED;
}
```

`SYS_WAIT`（`task.c:1661-1683`，修复前无任何校验）：

- **`wait(self)`**：CE 把自己当 child → `state = T_RUN` → `task_block` 永久阻塞 CE；
  而 shell 此刻正停在 `task_wait_child(CE)` 上等它 → **双方互等，无人可运行**；
- **`wait(0)`**：child = shell（`T_RUN`）→ CE 阻塞；shell 仍在等 CE → **同一死锁**。

`int 0x80` 是**中断门**，`cli` 语义下定时器 tick 无法打断该阻塞；`task_block` 是真正的阻塞
（不是忙等，CPU 反而空闲）。**没有任何第三方能唤醒任一方 ⇒ 死锁永久。**

**唤醒路径穷举证明**（team-lead 补充，我已逐处核对）：全树**不存在** `task_wake()` 这类函数；
能把 `T_WAIT_CHILD` 改回 `T_READY` 的只有三处，且**全部要求"被等的那个任务先死"**：

| 位置 | 条件 |
|---|---|
| `task.c:362`（`task_die_fault`） | `t->parent && t->parent->state == T_WAIT_CHILD` |
| `task.c:375`（`task_exit_current`） | 同上 |
| `task.c:408`（`task_kill`） | 同上 |

而 `wait(self)` 时被等待者是**自己**、`wait(0)` 时是 **shell**——两者都处于阻塞态，**永远不会执行到
"死亡"这一步**，所以上表三条唤醒条件永远不会成立。`maybe_autoreap`（`task.c:349-352`）只把
`T_ZOMBIE`/`T_UNUSED` 的**子**槽位回收，不唤醒任何人。

⇒ 这不是"等很久"，是"**永远不会被唤醒**"。**V-02 的 Q2 由代码决定，与并发度无关，不适用 W3 竞态折扣。**

### 8.4 C1 类（ring0 异常 → halt）的框架规则

> 这一条是**框架规则**，不是对 V-03 的定级。

`intr.c:138-168` 的两条路径：

- `(f->cs & 3) == 3`（ring3）：`intno==14` 先试 `task_page_fault()`（惰性 VMA，成功则 `return` 重试），
  否则 `fault_record()` + `task_die_fault()` —— **只杀该任务，控制台存活**；
- **其余（ring0）：无论 `intno` 是什么，一律** `fault_record()` → `cli` → `exc_dump()` → 可选
  `pf:` 细节行（仅 `intno==14`）→ 打印 `"ring0 kernel fault - system halted"` → `for(;;) hlt`。

**所以：ring0 侧只要抛异常，halt 是无条件的**，与"是页故障还是别的"**无关**。
（因此本框架的 Q2 判定不依赖那个还没定案的异常向量——这对 V-03 很关键。）
`pf:` 那行只是 `intno==14` 时的**附加细节**，它的有无**不能**反推向量：见 8.4.2。

由此 C1 类 finding 的级别**只由另外两个问题决定**：
- Q1：有没有跨边界（QEMU 退出 / 宿主文件变动）→ 有则 SEV1（W2）；
- Q3：halt 前有没有写坏镜像 → 是则 SEV1-b，否则 SEV1-a。

**由此得到一条对报告有用的观察**：`-no-reboot` + fail-stop halt 的设计，
把**任何**一次 ring0 异常都放大成整机不可用。这不是"漏洞"，但它是**严重性放大器**，
应在报告的"风险放大因素"一节单独说明：同样的 ring0 fault，在 Linux 上可能只是一次 oops，
在 CatOS 上是关机。

### 8.4.1 图形模式下的取证陷阱：屏幕全空 ≠ 没打印

V-03（A10）的日志 `tests/attack_logs/A10-gfx-overflow.txt` 里 `--- screen AFTER ---` 是**空的**，
`--- faultinfo probe ---` 也是空的。这**不是**"没走到 halt 路径"，而是：

- 攻击先 `display_mode(3)` 切到图形模式，**VGA 文本缓冲区的输出在图形模式下不显示**；
- `faultinfo` 是 guest 内程序，halt 之后它当然没有回应——halt 是 `cli` + `hlt` 死循环。

**结论：在这条攻击上，"屏幕上没看到 X"完全不能作为"X 没执行"的证据。** 当前的可靠证据只有：
`EIP=0x0101cd61`（`hlt; jmp -3`）、`HLT=1`、**`IF=0`**（说明 `intr.c:155` 的 `cli` 已执行）、
`CR2=0x7cfffffd`。`IF=0` 是"确实进了 ring0 halt 路径且越过了 `cli`"的硬证据。

### 8.4.2 异常向量怎么定案（不重建 ISO 也能查）

> **⚠️ 硬性前置条件（code-reviewer 提醒，采纳）**：`0x15FB780` **只对 `4dc87877` 这个 kernel.bin 有效**。
> 它是 `.bss` VMA `0x010cb000` + `g_fault_last` 符号偏移算出来的。**重建后必须用与工件对应的
> `kernel.pe` 重算**：`objdump -t build/kernel.pe | grep g_fault_last`。用错地址读到的是别的变量，
> 会得出"intno 是个莫名其妙的数"——**比不读更糟**。

`fault_record()` 在 halt 前（`intr.c:154`）已把记录写进 `.bss` 的 `g_fault_last`，halt 之后仍可从
monitor 读物理内存。字段布局**已按 `include/diag.h:8-16` 核对**（共 52 B = 13 字）：

| word | 字段 | 说明 |
|---|---|---|
| `[0]` | `valid` | 0 = 自启动以来无 fatal fault（读前先看这个） |
| **`[1]`** | **`intno`** | **CPU 向量——V-03 定案要的就是这个** |
| `[2]` | `ring` | 0 / 3，可交叉验证"确实是 ring0" |
| `[3]` | `tid` | -1 = 未知 |
| `[4..7]` | `task[16]` | 任务名 |
| `[8]` | `err` | 页故障错误码（`#PF` 时 `err&1=0` 表示 not-present） |
| `[9]` | `eip` | 应等于观测到的 `0x0101cd61` 附近 |
| `[10]` | `cr2` | 应等于 `0x7cfffffd` |
| `[11]` | `eflags` | |
| `[12]` | `ticks` | 故障时的 `timer_ticks` |

```
(qemu) xp /13xw 0x15fb780          # 仅 4dc87877；重建后重算
```
**验收式自检**：`[0]==1`、`[1]` 是 0–31 的合理向量、`[2]==0`、`[9]≈0x0101cd61`、`[10]==0x7cfffffd`。
五项同时对得上，才说明地址算对了。

**⚠️ 不能用 CR2 反推向量**：`fault_record(... cpu_cr2_read() ...)` 对**任何**异常都记录 CR2，
而 CR2 只在 `#PF` 时被硬件更新——非 `#PF` 时它是**上一次 `#PF` 的残留值**。

而且"残留值一定是用户地址"这个反驳**不成立**：本仓库 `tests/attack_logs/A02-arg-fuzz.txt` 里有
`[task 1 'ATKARGS' killed: page fault at eip=0x02080009 cr2=0xd0dad6cf]` +
`faultinfo` 显示 `page-fault ring0x3 … pf bits: not-present read user` ——
**这是 ring3 的 #PF，CR2 却是一个 `0xD0DAxxxx` 的大地址**。所以 ring3 缺页的 CR2 **可以**落在任何地方
（"一定是用户地址"只对惰性 VMA 那一类成立）。因此 stale-CR2 假设**比预想的更可行**，
`0x7cfffffd` 的"精确巧合"仍是**概率很低但非不可能**。

**结论**：CR2 匹配是强提示，**必须用 `intno` 定案**。

### 8.4.3 定案结果（2026-11-13 18:5x，实测，两次复现一致）

在 `SIDE=BEFORE` 工件（`tests/baseline-catos.iso` = `4dc87877`）上跑 `run /bin/ATKGFX.CE`，
halt 后读 `xp /13xw 0x15fb780`（新基线同一 `.bss` 布局，`objdump` 复核过）：

```
015fb780: 0x00000001 0x0000000e 0x00000000 0x00000001
015fb790: 0x474b5441 0x00005846 0x00000000 0x00000000
015fb7a0: 0x00000002 0x01005d48 0x7cfffffd 0x00010003
015fb7b0: 0x000003d2
```

| 字段 | 值 | 判读 |
|---|---|---|
| `valid` | 1 | 记录有效 |
| **`intno`** | **0x0e = 14** | **#PF —— 页故障，实测定案** |
| `ring` | 0 | ring0（内核态访存） |
| `tid` | 1 | |
| `task` | `0x474b5441 0x00005846` | ASCII：`ATKG` + `FX` = **ATKGFX** |
| `err` | **0x2** | write / **not-present** / supervisor（`err&4=0` → 不是 user） |
| **`eip`** | **0x01005d48** | **故障指令地址**（`fill()` 里的 store），**不是** halt 地址 |
| `cr2` | 0x7cfffffd | 与 `0xFD000000 + 0x7FFFFFFF*3 mod 2^32` 逐位一致 |
| `ticks` | 0x3d2 (978) | |

**结论**：V-03 的根因叙述按"`clip()` 有符号溢出 → 算出 `0x7CFFFFFD` 的 OOB 线性地址 → ring0 写 not-present 页 → #PF → halt"定案；
代码评审方的 `#PF` 推断**成立**，我此前基于"屏幕无 `pf:`"的"非页故障"读法**被实测否定**（屏幕空是图形模式所致，见 8.4.1）。

**⚠️ 自检项的两处教训（我第一版写错了，已改）**：
1. **`[9]` 是故障指令地址，不是 halt 地址**。本案例 `[9]=0x01005d48`、halt 在 `0x0101cd61`；
   把两者比较会误判"地址算错"。正确自检：`[9]` 落在内核代码段范围内 **且** `[9] != halt eip`。
2. **不能用 `HLT=1` 单独判定"进了 fault halt"**：内核空闲等键盘时也是 `hlt`（实测 `EIP=0x01000310`、**IF=1**、`valid=0`）。
   区分方法：**fault halt 是 `EIP=0x0101cd61` + IF=0 + `valid=1`**；空闲是别的 EIP + IF=1 + `valid=0`。
   （我在 AFTER 工件上第一次读到的就是空闲态，差点误读成"读不到/没 fault"——实际是**修复后不再 fault**，见下。）

### 8.4.4 顺带得到的 AFTER 侧实测（V-03 的修复验证）

在 `SIDE=AFTER` 工件（`kernel_v25/catos.iso` = `65b326f6`）上跑同一个 `ATKGFX.CE`：

- `g_fault_last.valid = 0`（**自启动以来无 fatal fault**）；
- `EIP=0x01000310`、`HLT=1`、**IF=1** → 内核**空闲**（shell 在等键盘），不是 halt；

这是 V-03 的 **AFTER 侧首个实测证据**（修复有效）。但注意它只证明"不再 fault"，
**不**等于"全部断言通过"——完整的 V-03 验收仍需确认 CE 正常结束（`ATK-DONE`）与控制台可交互；图形模式下屏幕为空，需用 `faultinfo`/后续命令探活（见 8.2）。

## 9. 附：一个已经可见的参考案例（用于校准尺子）

`task.c` 的注释描述了这样一条路径（**本轮代码里已能看到针对它的 ring0 保护，但被测 ISO 是否包含
该保护以实测为准**）：

> 任意 CE（由 shell 派生，继承 `UID_ROOT`）调用 `api->kill(0)` → 对 shell（TID 0）执行
> `task_cleanup()` → 该槽位变 `T_UNUSED`，**没有东西会重生它** →
> 「机器还在跑，但 prompt 永远没了」——注释原文称之为 "the cheapest possible denial of service,
> no kernel fault needed"。

按本框架定级：
- Q1 无跨边界 → 否；Q2 控制台**不可恢复**（S2：无 respawn）→ 命中 SEV1；
  Q2b 重启后正常（磁盘未被动过）→ **SEV1-a**（重启即恢复，镜像不用动，无 `/` 数据丢失）；
- 不适用 W5/W6 折扣（它就是"只是 shell 挂了"，而在这里那就等于整机报废）；
- 恢复手段：`system_reset` / 重启 QEMU（镜像未坏，无需重拷）；
- 触发前提：`run` 任意恶意 .ce —— 归入"正常用法下即可触发"。

这个案例的作用是校准：**它看起来"只是把一个进程杀了"，但在 CatOS 上必须是 SEV1。**
如果红队战果里有同类现象（控制台丢失），一律照此定级，不要因为"没 panic"而降到 SEV2/3。
