# CATOS-PROP-001 评审意见（G2 连续曲率圆角）

- 评审人：主代理（CatOS 工程裁决）
- 日期：2026-11-25
- 结论：**有条件通过，但原案的技术前提有一处硬错误，成本与字段设计需重写**
- 落地版本：cap2 半径收口后作为 cap3 第一批（排在 alpha/折行/缓动之后，与滚动条统一并行）

## 1. 事实核对（决定整个提案要不要按原样做）

| 提案断言 | 代码事实 | 结论 |
|---|---|---|
| 「当前圆角只有四分之一圆弧（ARC）」 | `kernel_v25/src/gui/paint.c::calm_masks_init()` 用 `u^5+v^5` 生成覆盖率掩码，注释明写「超椭圆 n≈5」 | **错误**。现有圆角已经是超椭圆，不是圆弧 |
| 「G2 指数 n≈4.5–5 是新增能力」 | `CALM_R_N=4`、`CALM_RADII={8,12,16,24}`、掩码 `calm_mask[4][24][24]` 启动期生成，n 固定 5 | 部分成立：n=5 已有，n=4.5 与「可显式选形态」没有 |
| 「预生成覆盖率表，ROM +0.9 KB」 | 掩码是 `.bss` 运行时生成（`static uint8_t calm_mask[4][24][24]`＝2304 B），不是 const ROM 表 | **估算对象错了**：增量是 RAM，不是 ROM |
| 「块记录 40 B 增至 42 B」 | 40 B 的是 `ce_blk_rec_t`（CE 声明通道）；内核内部 `blk_spec` 远大于 40 B 且已是 append-only | **对象错了**：内部字段追加零成本，CE 侧走 `ce_blk_rec2_t`，不动 40 B 旧记录 |
| 「超椭圆命中测试需同步支持」 | 命中始终按矩形判定，圆角从不参与 hit test | **不成立**，无需改命中 |
| 「app 风格也用圆弧半径」 | `calm_shape_eligible()` 仅在 calm 风格生效；app 风格当前是直角，没有 ARC 路径 | 现状是「calm=超椭圆 / app=直角」，ARC 实际不存在 |

一句话：**提案想补的东西，一半已经在 `calm_mask` 里，只是被锁死在 calm 主题、n 固定 5、覆盖率精度偏低（80% 内全不透明 + 线性斜坡，不是面积采样）。** 所以正确的工作不是「新增 G2」，而是「把已有超椭圆解耦成可显式选择的形态，补 ARC 作为对照档，并把覆盖率精度做实」。

## 2. 修订后的设计（以此为准）

### 2.1 字段（append-only，落在 `blk_spec`/`block`，CE 走 rec2）

| 字段 | 类型 | 取值 | 默认 | 说明 |
|---|---|---|---|---|
| `corner_shape` | u8 | 0=ARC，1=SQUIRCLE | 0 | 与 `corner_tl/tr/br/bl` 正交；整块统一，不逐角混用 |
| `corner_n` | u8 | 0=默认(50)，45，50 | 0 | n×10；仅 SQUIRCLE 有效，只收 4.5/5.0 两个预生成档，其它值钳到 50 并 `WARN_RADIUS_N_RANGE` |

不新增 `radius_n=45` 每块任意值——表驱动只能有预生成档位，否则就是假承诺。

### 2.2 HTML 侧（与《HTML 原型开发规范 v3》命名纪律一致，一属性一职责）

```html
<div data-radius="16" data-radius-shape="squircle">…</div>
<div data-radius="16" data-radius-shape="arc">…</div>
<div data-radius="16 16 0 0" data-radius-shape="squircle" data-squircle-n="4.5">…</div>
```

- 不再用 `data-radius="g2 16"` 把关键字塞进数值属性（解析脆弱、与逐角写法冲突）。
- `g2` 仅作别名保留在转换器里（读到 `g2` 前缀等价 `squircle`），规范正式名用 `squircle`。
- `data-squircle-n` 只接受 `4.5` / `5`，其它报 `E_RADIUS_N_BAD`。

### 2.3 覆盖率表与内存

- 三套表：`ARC(4 档) / SQ5(4 档) / SQ45(4 档)`，每档每角 24×24（不是提案写的 16×16——现有档位 24 需要 24×24）。
- 生成算法改为 **4×4 子采样求面积覆盖率**（16 个采样点判定 `|x|^n+|y|^n ≤ R^n` 的比例），替换现有「80% 内全 255 + 线性斜坡」。这是本次真正的质量提升点，也是「误差 ≤1/255」验收能过的前提。
- 内存：3 套 × 2304 B ≈ 6.9 KB `.bss`。**主代理批准**（单数组 2304 B，未超 4 KiB 红线；合计超 4 KiB，要求构建后复测 `_bss_end` 距 CE 基址 `0x02000000` 仍 ≥64 KiB，并在实现文档写明）。
- 只在需要时惰性生成：首帧出现 `arc` 或 `n=4.5` 才建那套表；只用默认 squircle 的构建不付 6.9 KB。

### 2.4 与 cap2 的衔接

- cap2 正在做 `corner_tl/tr/br/bl` 显式逐角；本项只在其上追加「形态」维度，不改逐角/贴边/同心语义。
- 贴边角仍强制半径 0；同心仍 `子 = 父 − padding`；HC 仍 radius=0（形态自动失效）。
- 单块内四角形态必须一致（R-7.5-03），避免「三角超椭圆一角圆弧」这种不可解释的混合。

## 3. 成本重估

| 项 | 原提案 | 修订后 |
|---|---|---|
| 记录宽度 | +2 B（40→42） | 内部 `blk_spec` +2 B（append），CE 旧记录 0 改动 |
| ROM/RAM | +0.9 KB ROM | ≈ +6.9 KB `.bss`（惰性生成，可只建实际用到的套） |
| 代码 | ~120 行 | ~180 行：表生成改面积采样、三套表、选择分支、转换器与诊断 |
| 风险 | 低 | 低，但比原估多一项「重写掩码生成」——这恰好修掉现有覆盖率精度不足的老账 |

## 4. 验收（在原案基础上收紧）

| 指标 | 阈值 | 测法 |
|---|---|---|
| 角部覆盖率误差 | ≤1/255 | 与解析超椭圆（4×4 子采样参考值）逐点比，8 点采样 |
| n=2 回归 | 0 字节差异 | 用同一生成器以 n=2 生成，与解析圆弧表逐字节一致（证明生成器正确） |
| ARC vs SQ5 差异 | 角中间段 ≥3/255 | 证明确实换了几何，不是参数没生效 |
| 拼缝 | 0 px | 9-slice 边界扫描 |
| 平均帧 | 不劣于当前 calm 同场景 | 拖动/展开 60 帧采样 |
| 构建红线 | `_bss_end` 距 CE 基址 ≥64 KiB | `check_link_layout.py --strict` |

## 5. 对原案「未决问题」的裁决

1. **字段宽度**：不新增 42 B 记录；内部 append、CE 走 rec2。
2. **是否加 32 档**：否。800×600 上 24 已够；加档会让「档位→表」尺寸不一致（现有表按 24×24 分配）。要加就 ARC/SQ 一起加，且单独提案。
3. **CE 是否暴露**：是，随 `ce_blk_rec2_t` 一起开放 `corner_shape`，不发 `corner_n`（只给默认 5.0）；命中测试不变（矩形）。
4. **命名**：正式名 `squircle`，`g2` 作为转换器别名。

## 6. 优先级

- 排在 cap2 半径收口之后，与「滚动条统一」并行；不与 alpha/折行/缓动抢同一批文件。
- 先落「形态字段 + 表选择 + 面积采样重写」；`n=4.5` 表可以第二批，先保证 ARC/SQ5 两套正确。

## 7. 给提案人的一句话回复

> 方向对，但「现在只有圆弧」不成立——`calm_mask` 早就是 n=5 超椭圆，锁在 calm 主题里而已。所以这次做的是「解耦形态 + 补 ARC 对照 + 把覆盖率从 80% 线性斜坡改成 4×4 面积采样」，成本从 0.9 KB ROM 变成 6.9 KB RAM（惰性），但顺带修掉现有圆角精度欠账。
