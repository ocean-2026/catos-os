# v2.72 补充说明（VMware 反馈轮）

本轮针对 VMware 上反馈的三条渲染现象 + 一条声卡现象做处理，并把 v2.72 里
"sshd 开机自启动"删掉。**能自证的已经自证，不能自证的写明为什么。**

## 1. 字体底色 ≠ 背景色（渲染 #4）

根因不是 alpha，也不是字体缓存：**主题应用得太晚**。

`shell_run()` 的启动顺序原来是
`boot_apply_videomode()` → `pal_apply_scheme()`。前者切到 vbe24 时用当时的
背景色（默认 `#0C0C0C`）清了一整帧；后者随后把 `PAL_BG` 换成注册表里的主题色
（例如 `#0A0E14`）。**之后只有被"写"过的单元格用新底色，没人重画的地方还是旧底色**，
于是字块和背景出现色差，且留下一个矩形边界。

修法两条：
1. 启动顺序改为 **主题先应用，再切显示模式**；
2. `pal_apply_scheme()` 结尾调用新增的 `con_repaint_frame()`：
   `be->clear(s_bg_rgb)` + 全格重绘，文字不丢，整帧同色。

`con_clear()` 不能用——它会把文字一起清掉。

## 2. 开机几秒的频闪（渲染 #2）

同一条链路上还有两次多余的全屏清屏：

| 位置 | 原来 |
|---|---|
| `v24_enter_svga()` / `v24_enter_bochs()` | 切模式后再 `gfx24_clear()` 一次 |
| `v24_set_scale()` | 又被 `size_restore()` 调起，再清一次 |
| `switch_backend()` → `redraw_all()` | 又 `be->clear()` 一次 |

在 VMware SVGA 上每一帧都会被宿主以 25 Hz 重贴（`svga_tick()` → `svga_flush()`
发 `SVGA_CMD_UPDATE` 全屏矩形），所以**连续三次全屏清空=肉眼可见的闪三下**。
现在只保留 `redraw_all()` 那一次，`enter()` 与 `set_scale()` 都不再清屏。

## 3. 分辨率"不严丝合缝"（渲染 #3）

先把事实钉住：`svga_mode_set()` 本来就会回读 `SVGA_REG_WIDTH/HEIGHT` 并在
不一致时 `goto fail`，所以**"要 800x600 却真给了别的尺寸"这条路不存在**。
截图里那块颜色不同、边界正好 640x400 的矩形，是上面第 1 条留下的旧底色
（640x400 = 80×25 文本模式的像素范围，正好是切换前那一帧的大小），不是
"VMware 给的屏幕比要的小"。

因此这一条的修法就是第 1 条：整帧统一重绘，边界自然消失。另外为了以后能从
日志而不是截图定位，启动时多打一行真实几何：

```
[display] boot mode: vbe24 (800x600, 100x37 cells @8x16)
```

`vdiag` 里仍然有 pitch/stride/lfb/bar 的原始值。

## 4. 声卡（VMware ES1371 无声）

**没有盲改。** 现状是拿 ES1370 的寄存器布局去编程 ES1371：DAC1 走
MEMPAGE=0xc 窗口的 `0xc30/0xc34`、采样率走 `CTRL` 的 `WTSRSEL` 两位。
ES1371 的 AK4531 codec 是**只写**接口，读不回来；没有实机读数就写序列，
等于把"没声音"换成"可能是另一组寄存器写坏了"，而且无法验证。

本轮加的是取证工具：`sndregs` 直接打印原始寄存器。

```
snd: ensoniq id=1274 dev=5000 io=0xc000 irq=11 ready=1
  CONTROL=0x100  STATUS=0x60  SERIAL=0x83
  SCOUNT=0x0  FRAMECNT=0x0  PORT20=0xd3
  rate=5512 bufsz=65536
```

判读方法（也已写在命令输出里）：

- 播放时 **FRAMECNT 不动** → DMA 根本没被 arm（寄存器布局/采样率编程错）；
- 播放时 **FRAMECNT 在动但没声** → AK4531 仍处于静音，需要 codec 初始化。

`dev=1371` 时命令返回 `$?=3`（"设备认出来了，通路未验证"），不会假装成功。

## 5. 删除 sshd 开机自启动

- 不再向 `/etc/autoexec/` 播种 `sshd.sh`；
- `@sshd` 的内置守护分支删除（该分支只为开机启动 sshd 而存在）。

`sshd` / `sshd -d` 手动启动仍然可用。理由：一个开机就监听的 :22，加上尚未
做签名校验的 `pkg` 通路，是负债不是特性。

## 6. 其他

- `about` 的 logo：首行与末行各加一个前导空格（按反馈）。
- 启动 banner 的版本号从 `v259` 更正为 `v2.72`。

## 验证

- `-vga std`（Bochs dispi）：整帧 `#0C0C0C` 单一底色，文字区无矩形边界；
  `sndregs` 在 `-device es1370` 下输出上述原始值，无异常。
- `-vga vmware`：QEMU 6.2 的这个 VGA 设备无法完成 GRUB 的 VBE 模式设置，
  开机黑屏，**因此本轮没有在 QEMU 上复现 VMware SVGA 路径的像素结果**。
  需要你在 VMware 里跑一次：看启动行 `[display] boot mode: ...`、`vdiag`、
  `sndregs`，把输出发我，我再据实修正。

## 第二轮（VMware 实机回读后的追加修复）

实机两张截图说明第一轮「整帧重绘」**没有解决**底色不一致，只是换了个样子：
截图 801×599 里，x 0..640 / y 0..400 是 `#0A0E14`（单元格底色），其余仍是
`#0C0C0C`（旧的清屏色）。边界 640×400 正好是 80×25 × 8×16 —— 也就是
**切模式那一刻的旧网格**。

结论：模式切换过程中的某一次 `clear + redraw` 用的是切换前的网格几何
（80×25），于是整帧只有 640×400 被刷成主题底色；之后 `size_restore()`
把网格改成 100×37，但没有任何一次「以最终几何整帧重刷」，剩下的一圈
永远是旧底色。同理，`vdiag` 报告 `pitch=0xC80`(3200)、`800x600`，
说明模式协商本来就是对的 —— 看到的「不严丝合缝」是这块残留，不是分辨率错。

修法：`boot_apply_videomode()` 在 `size_restore()` **之后**、
打印 boot 几何行之前，补一次 `con_repaint_frame()`（整帧 `be->clear(主题底色)`
+ 全格重绘）。这是最后一句话的时机，之后的输入不会再改变底色。

另加 `fprobe`：整帧填黑 + 四角四色块 + 四边框。VMware 上跑它即可判定
「宿主显示面是否真等于我们编程的模式」：角块被切掉 = 宿主面更小（问题在
SVGA 模式设置）；四个角都在 = 面正确，问题只在控制台绘制路径。

## 第三轮（定时任务复查时追加）

- `sndmap`：**只读** dump 整个 `0x00..0x3C` 寄存器窗口（每次 4 字节）。
  读操作不改变器件状态，所以在 VMware 的 ES1371 上也是安全的。用途：
  确认哪些偏移是真正可回读的 RW 寄存器。实机 `sndregs` 已给出
  `PORT20=0x83`（我们写的是 `0x0c`），说明 ES1370 那套偏移映射在这颗
  芯片上不成立；`sndmap` 的整张表能把 ES1371 的真实布局钉下来。
- 文档更名：`docs/v2.72-变更说明.md`（原 `v2.72-补充说明.md`）。

## 第四轮：静态分析定位到根因（两套背景色）

用户反馈澄清了关键事实：**文字是按屏幕宽度排的（网格 100×37 正确），只有背景色
没铺满屏**。因此不是分辨率协商问题，也不是"字体底色"问题，而是**画布底色有两套，
互相不一致**。

证据链：
- `render.c` 的内建主题 `g_dark_tokens[0]`（canvas）= `#0A0E14`；
  它在 `con_init()` 末尾 `con_apply_theme(1)` 里生效，并把
  `s_bg_rgb` 设为 `#0A0E14`；
- `palette.c` 的 `k_defaults[PAL_BG]` 与 hive 种子
  `HKLM\Software\CatOS\Terminal\Colors\Background` = `#0C0C0C`；
  v2.67 起开机走 `pal_apply_scheme()` + `con_set_style_rgb(pal_rgb(PAL_BG))`，
  于是 `s_bg_rgb` 又变成 `#0C0C0C`；
- 单元格在写入时**快照**当时的 `s_bg_rgb`（`cell_blank`/`cell_set` 复制到
  `c->bg`），所以先落的格子带 `#0A0E14`、后落的带 `#0C0C0C`；
  `redraw_all()` 还会跳过 `cp==0 && bg==clear_bg` 的空格——被跳过的地方就永远
  留着另一套颜色。屏幕上表现为"文字区域是深蓝黑、其余是灰黑"的补丁状边界。

版本对照：v2.66 只有 `con_apply_theme()` 一个来源（单套颜色），从不出问题；
v2.67 引入 hive 颜色角色作为第二来源 → 问题开始；v2.68.1 之后一直继承。

修法（三处，同一件事：只留一个"背景"定义）：
1. `palette.c`：`k_defaults[PAL_BG]` 与静态初值改为 `0x0A0E14`，与内建主题对齐。
2. `hive.c`：种子 `Colors\Background` 改为 `#0A0E14`。
3. `render.c::con_set_style_rgb()`：背景色变化时，把**所有** `bg == 旧默认色`
   的格子重新盖成新色（显式设置过背景的面板/反显不受影响）；
   `theme` 命令与开机流程随后各补一次 `con_repaint_frame()`。

验证（QEMU `-vga std`，整帧 4 像素步进统计）：修前存在 `#0C0C0C` 与 `#0A0E14`
两种底色；修后整帧只剩 `(10,14,20)` 一种底色（另加文字色），`uniq=4`。

## 第五轮：补上"颜色可运行时修改"这条链

原先的设计缺口（用户实测发现 `reg set` 改底色"没反应"）：
1. `pal_reload()` 写了却没有任何调用点 → 颜色只在开机 `pal_init()` 读一次，
   改完必须重启；
2. 开机还会 `pal_apply_scheme(Theme)` 把整张角色表按内置方案重写，
   **用户刚用 `reg set` 写进 `Colors\Background` 的值会被无声覆盖** ——
   看上去就是"注册表改了没用"。

改法：
- 开机不再重放 scheme：hive 是唯一事实源，`Theme` 仅作标签；
  `theme <name>` 仍是"整表重写"的显式入口。
- 新增 `colors` 命令（补齐运行时的另一半）：
  - `colors` 从 hive 重读全部角色 → `con_set_style_rgb` → `con_repaint_frame()`，立即生效；
  - `colors save` 持久化；
  - `colors reset` 恢复内置默认并应用（新增 `pal_reset()`）；
  - `colors set <role> <#RRGGBB>` 写单个角色并立即重绘。
- 命令表 / TAB 补全 / help 均已登记。

验证（QEMU `-vga std`，整帧 4 px 步进统计）：
- 开机画布 (10,14,20) = `#0A0E14`，`uniq=4`；
- `colors set background #101418` 后整帧变 (16,20,24)，`uniq=5`（只有画布那一色变了）；
- `colors reset` 后回到 (10,14,20)。
