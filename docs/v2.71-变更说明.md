# v2.71 变更说明 —— 内核 SSH-2 服务端

**主题**：CatOS 内核原生 SSH-2 服务端（`sshd` 命令）。宿主 OpenSSH / paramiko
可通过 QEMU slirp 端口转发（`hostfwd=tcp::2222-:22`）或 VMware NAT 直接连入，
拿到 CatOS shell（exec 单命令 + 交互式 shell 通道）。

## 新增

### 1. 密码学原语（`crypto.c` / `crypto.h`，~950 行）

全部 C 实现，无外部依赖；宿主自测（`-DCRYPTO_SELFTEST`，mingw32 i386 与内核
同 32 位同源码）12 项全 PASS，Ed25519/X25519 经 libcrypto（`cryptography`）
逐字节交叉验证：

| 原语 | 说明 |
|---|---|
| SHA-256 | 空串 / `abc` / 63B / 119B 边界回归全过 |
| HMAC-SHA256 | RFC 4231 用例验证；支持两段拼接消息（MAC 用） |
| AES-128-CTR | S-box 运行时生成（GF(2^8) 逆 + 仿射）；**128 位大端计数器跨包连续 keystream**（RFC 4344 SDCTR，OpenSSH 兼容）；FIPS C.1 逐轮对照 |
| SHA-512 / X25519 / Ed25519 | TweetNaCl（公有领域）逐字移植（gf[16] 字段运算、ge_add、modL 等）；X25519 agreement 与 libcrypto 一致 |
| `crypto_random` | rdtsc 混合 xorshift64*（演示级熵，v2.71 可接受） |

### 2. TCP 服务端（`netstack.c` / `net.h`）

独立 `tcps` 上下文，与既有 TCP 客户端共存：
`net_tcp_listen(port)` / `net_tcp_saccept()` / `net_tcp_ssend()` /
`net_tcp_srecv()` / `net_tcp_srecv_all()` / `net_tcp_sclose()`。

- SYN→SYN+ACK→ESTABLISHED 三段握手；**握手 ACK 可能捎带首个数据段
  （客户端 banner），必须 fall-through 处理**（否则双方互等死锁）。
- 接收缓冲 16KB，带去前缀压实；`srecv_all` 精确 n 字节阻塞读（~30s 空闲超时）。

### 3. SSH-2 协议栈（`ssh.c` / `ssh.h`，~780 行）

忠实移植宿主原型 `deliverables/ssh-prototype/sshd_min.py`（v2.70 已验证）。
曲线 `curve25519-sha256`，主机密钥 `ssh-ed25519`，加密 `aes128-ctr`，
MAC `hmac-sha2-256`（非 EtM）。要点（header 注释 8 条铁律）：

1. 交换哈希 H = SHA256(s(V_C)‖s(V_S)‖s(I_C)‖s(I_S)‖s(K_S)‖s(q_c)‖s(q_s)‖mpint(K))，
   全部字段带 4 字节长度前缀；**I_C/I_S 含 msg 字节 20**。
2. Ed25519 直接签 H；sigblob = s("ssh-ed25519")‖s(sig64)。
3. 密钥派生 `SHA256(mpint(K)‖H‖letter‖H‖prev)` 链式；收向 A/C/E，发向 B/D/F。
4. aes128-ctr 加密**整包（含 4 字节长度字段）**，CTR keystream 跨包连续。
5. MAC = HMAC(mac_key, seq‖明文包)。
6. **padding 按 16 对齐**（RFC 4253 §6：整包必须是 cipher block size 或 8
   的较大者 = 16）。⚠️ 8 对齐会被 OpenSSH（`padding error: ... mod N`）与
   paramiko（`Invalid packet blocking`）同时拒绝——原型侥幸全落在 16 上。
7. SERVICE_REQUEST/ACCEPT 在 NEWKEYS 与 USERAUTH 之间完成。
8. channel request 体：recipient(4) 再 string type。

**一条连接多通道**：paramiko 在同一 TCP 连接上复用通道（exec 之后开 shell），
serve 循环按通道服务直到 DISCONNECT/断连；`pty-req`/`window-change`/`env`
回 SUCCESS（paramiko `_request_failed` 会直接关通道，不能回 FAILURE）。

### 4. shell 集成（`shell.c`）

- `sshd` 命令：net_up → DHCP → listen(22) → accept 循环；ESC 退出
  （必须用 `kb_getkey_timed(2)`，`kb_getkey` 遇修饰键永久阻塞）。
- `shell_ssh_exec_line()`：tee 捕获控制台输出（`\n`→`\r\n`）、
  `g_script_mode=1` 防分页阻塞、`g_last_rc` 回传退出码。
- 未知命令补 `g_last_rc = 127`（POSIX 惯例，SSH exit-status 需要）。

## 调试历程（血泪教训）

| 现象 | 真因 | 修法 |
|---|---|---|
| Signature verification failed，双端 H 不同 | **Kmp 双重长度前缀**：S.Kmp 已是完整 string，组 H 时又包了一层 `ssh_put_str` | 直接 memcpy 追加 |
| H 修完签名仍失败 | **sigblob[80] 装不下 83 字节**（4+11+4+64），栈溢出踩坏数据 | 扩到 96；固定向量实验（guest/宿主同输入签名逐字节一致）证明算法无辜后锁定发送路径 |
| exec 有输出但 rc=255（padding error）/paramiko Invalid packet blocking | **8 字节对齐**（AES 要求 16） | pad 公式改 16 |
| paramiko shell 通道 EOF | DATA 解析 offset 用 1，把 recipient 当 string 长度（应为 5） | 修正偏移 |
| paramiko 第 2 个通道无响应 | 单会话模型，同一 TCP 连接的新 CHANNEL_OPEN 无人读 | 重构为连接级多通道循环 |
| exit-status rc=0 | 未知命令未设 `g_last_rc` | 补 127 |

调试方法论：**MITM 录包代理 + paramiko monkeypatch dump + guest 全量 hb hex
dump（vga_write 打点 + monitor screen_text 读取）三侧对拍**，逐字节定位。
探针：`tests/ssh_hdiff_probe.py`（差分对拍）、`tests/ssh_step2_probe.py`
（聚焦诊断）、`tests/ssh_v271_probe.py`（6 项验收）。

## 验收

`tests/ssh_v271_probe.py` **6/6 PASS**：

1. sshd 监听 22 端口就绪
2. OpenSSH exec `echo` 回传 marker（rc=0）
3. OpenSSH exec `uname` 报 CatOS 身份
4. paramiko 交互式 shell 通道（pty-req + shell 请求 + echo 回显）
5. 失败命令 → exit-status 127
6. guest 控制台可见会话开关

局限（记入已知问题）：每会话重新生成主机密钥（无持久化，known_hosts 会变）；
接受任意认证（v1，先打通协议）；RNG 为演示级熵；窗口流控未实现
（发送量小，够用）。
