## 0. 不可动摇的约束（任何阶段都不得违反）

| # | 不变量 | 理由 |
|---|---|---|
| I1 | `catos_api_t` / syscall enum **append-only**，只在尾部追加 | 老 `.ce` 按偏移索引函数指针表，插字段即错位崩溃 |
| I2 | 每阶段收尾必须通过 QEMU 实机回归 `tests/qemu_regress.py` **12/12**，以及 4GB / btop / dl / bg 四个探针 | 这是项目唯一的质量锚点，失去它等于失去可验证性 |
| I3 | 安全修复 A10（`be_vbe24.c` 的 `int64_t clip()`）、H1（ring3 不可 kill ring0）、H8（`/bin/*.ce` 只读封印）、H9（autoexec 只列出不执行）必须持续保留 | 隔夜包曾回退这四项，合并时已重新施加 |
| I4 | **外部表现大多不变**：shell 命令集、CE 程序用法、gfx/text 切换、交互流程保持原样；native 能力是**叠加**不是替换 | 用户明确要求；通用化是内部革命 |

| I6 | 构建前 `export PATH=/c/msys64/mingw32/bin:$PATH` | 脚本内 `/d/Tools/MSY32/...` fallback 已损坏 |
| I7 | 每个阶段都要有可运行产物，禁止"大爆炸式"重写后一次性合并 | 双人格并存，旧树始终可启动 |

## 1. 目标态：什么叫"通用 OS"达成

分层定义，全部满足才算达成；每项都给出可检验判据。

| 层 | 目标态 | 判据 |
|---|---|---|
| **外部表现** | **与当前基本一致，用户零迁移** | shell 命令、CE 程序、gfx/text、btop/后台任务照常工作；新能力为增量 |
| 硬件 | 64 位 x86-64，4 核 SMP，识别 4GB+ 内存 | QEMU `-m 3840 -smp 4` 下 shell 正常，4 核均有负载 |
| 内核 | 独立地址空间 + COW + swap + 抢占式多核调度 | `fork` 后父子内存隔离；多线程任务跨核运行 |
| 存储 | VFS 抽象 + ext2/ext4 + FAT32 并存 | `mount -t ext2` 挂真实镜像，跨文件系统路径统一 |
| ABI | native 数字 syscall（版本化）+ legacy CE 人格并存 | 同一内核同时运行 `hello.ce` 与 ELF64 `hello` |
| 用户态 | 自有 libc + 用户态动态链接器 + 交叉工具链 | 从源码编译并运行一个真实 C 程序 |
| 网络 | socket API + 完整 TCP | 能向外部 HTTP 服务发起 GET 并读回响应 |
| 安全 | POSIX 凭据 + 能力位 + NX/SMEP/SMAP + KASLR | 普通用户无法读内核内存、无法 kill 内核任务 |
| 生态 | 包管理依赖解析 + 自举环 | 系统内编译系统自身（阶段性） |

**明确非目标**：X11/Wayland 兼容、桌面环境、GPU 加速、Linux 二进制兼容、多用户远程登录。
**明确不变**：shell 提示符、命令拼写与参数、`gfx`/`text` 切换流程、CE 应用运行方式、后台任务语法。

## 2. 双人格架构（总设计）

```
用户看到的东西（全程不变）
  shell · 命令集 · CE 程序 · gfx/text 终端 · btop/后台任务
                       │
        ┌──────────────┴──────────────┐
        │                             │
  legacy personality            native personality
  CE01 / CSO1                   ELF64 / .so
  int 0x80 thunk                syscall + vDSO
  catos_api_t（冻结）            数字 syscall 表（版本化）
        │                             │
        └──────────────┬──────────────┘
                       │
                统一内核核心
     VMA / 调度 / VFS / 网络 / 驱动 / 显示后端
```

- **用户视角恒定**：无论内部跑哪套人格，用户始终用同一个 shell、同一套命令。native 人格
  只是让系统"能跑更多程序"，**不改变用户与系统的交互方式**。
- **legacy personality**：现有全部代码原样保留，跑在 IA32 兼容模式，`int 0x80` 入口不变。
- **native personality**：新建，long mode，数字 syscall，自有 libc（POSIX 形状但不承诺二进制兼容）。
- 两者共用内核核心，但**不共用 ABI**；禁止把 `catos_api_t` 改造成通用 ABI（I1）。

## 3. 四阶段执行计划

> 阶段安排已按"外部表现尽早恢复"调整：P0 是纯内部地基（允许只有串口输出），
> **P1 收尾就把 shell 与显示后端移植到 64 位内核**，让用户可见外观回到与 v25 一致，
> 之后的 P2/P3 都是在这个"外观不变的壳"里继续换内部。

### P0 — 64 位地基（预计 2–4 周）

**目标**：证明 64 位内核能独立启动并运行一个 ELF64 用户程序；此阶段完全不接 CE、不接图形后端（过渡态）。

| # | 任务 | 交付 | 状态 |
|---|---|---|---|
| P0.1 | 新建 `kernel64/` 平行树，GRUB 引导进 long mode | `kernel64/` 骨架 | ☐ |
| P0.2 | PML4 四级页表 + higher-half 内核映射 | `paging64.c` | ☐ |
| P0.3 | 移植 PMM 到 64 位；解析 multiboot mmap，支持 4GB+ | `pmm64.c` | ☐ |
| P0.4 | long mode IDT + 异常处理；COM1 串口 early printk | `idt64.c`, `serial.c` | ☐ |
| P0.5 | syscall MSR 初始化（STAR/LSTAR/CSTAR, EFER.SCE） | `syscall64.c` | ☐ |
| P0.6 | 最小 ELF64 加载器（PT_LOAD），跑通 ring3 `hello` | `elf64.c` + demo | ☐ |

**验收**：`qemu-system-x86_64 -m 3840 -smp 4 -cdrom kernel64/catos64.iso` → 串口输出 shell prompt；
ELF64 `hello` 打印成功；旧树 `kernel_v25` 回归仍 12/12。

**回退**：`kernel64/` 完全独立，出问题直接回到 `kernel_v25`，零污染。

### P1 — 内核核心通用化 + 外观回归（预计 4–8 周）

**目标**：补齐通用 OS 的内核能力；这是旧路线图判定"不做"的三项转正的地方。
**阶段结束时，64 位内核的用户可见行为必须与 v25 一致**（shell、gfx、CE 程序照常）。

| # | 任务 | 交付 | 状态 |
|---|---|---|---|
| P1.1 | VMA 线性链表 → 红黑树 | `vma.c` 重构 | ☐ |
| P1.2 | `fork()` COW；页错误路径处理写时复制 | `fork64.c`, `pf64.c` | ☐ |
| P1.3 | slab 分配器 + per-CPU 缓存 | `slab.c` | ☐ |
| P1.4 | swap 页（镜像后端），页面回收 | `swap.c` | ☐ |
| P1.5 | APIC 定时器 + 每 CPU 运行队列 + CFS 类调度 | `smp.c`, `sched64.c` | ☐ |
| P1.6 | 内核同步原语：自旋锁、互斥锁、RCU | `sync.c` | ☐ |
| P1.7 | 动态任务表，突破 `MAX_TASKS 16`；线程组 | `task64.c` | ☐ |
| P1.8 | VFS 抽象（superblock/inode/dentry/file）+ ext2 驱动 | `vfs.c`, `ext2.c` | ☐ |
| P1.9 | **外观回归**：把 shell 命令集、`be_text`/`be_gfx` 后端、CE 人格移植到 64 位内核 | `shell64.c`, `compat32/`, 后端移植 | ☐ |

**验收**：`-smp 4` 下 4 个 CPU 都有执行时间；`fork` 后父子写同一页互不影响；
`mount -t ext2` 挂上真实 ext2 镜像并读写文件；
**用户可见行为与 v25 一致：shell 命令、`gfx`/`text` 切换、CE 程序、btop、后台任务全部照常**；
I2 全部探针 PASS。

**风险**：打开内核抢占会动摇依赖非抢占的 static 缓冲安全（旧路线图第 14.2 条）。
**前置**：先把 `copy_from_user()` 快照化扩展到所有 syscall 路径，再开抢占。

## 5. 显示子系统：图形模式的定位与边界

> **最容易被误解的一节。用户已明确：图形模式只是 shell 的图形后端，
> 是"更自由的文本模式"，主要为命令行。它不是一个独立的图形环境，也没有自己的应用体系。**

### 5.1 现状（准确描述）

- 前端 `be_text` / 后端 `be_gfx`，`render.c` 开机默认切 `be_gfx`（Mode 13h / VBE，640×400 级分辨率）。
- `be_gfx` 本质是**彩色文字终端**：字形点阵渲染 + 前景/背景色 + 软终端网格（窄屏 40×12 自适应）。
- 已具备：`gfx_info` / `gfx_rect` / `gfx_blit`（syscall 61/62/63）、`gotoxy`（65）、像素级图元。
- `text` 命令保留物理按键 Y 确认才切回文本——这是安全护栏，不是 GUI 行为。
- btop 已证明：同一套命令行程序在 gfx 后端下自适应渲染，无换行/残影。
- **用户看到的图形模式里只有 shell**——没有窗口、没有桌面、没有独立 GUI 程序，
  这就是它应有的样子，通用化后依然如此。

### 5.2 演进方向（全部保持命令行语义）

| # | 增强 | 目的 |
|---|---|---|
| D1 | VBE LFB 高分辨率 + 可缩放字模 | 字符更多、更清晰；API 不变 |
| D2 | 自由像素坐标 + 文本层 z-order（`gotoxy` 扩展） | 比 80×25 更自由的排版 |
| D3 | 双缓冲 / 翻页 | 消除滚动与动画闪烁 |
| D4 | UTF-8 / 16×16 中文点阵 | 终端输出一致化 |
| D5 | TUI 构件库（面板/菜单/边框，纯字符语义） | 让命令行程序写出更好的界面 |
| D6 | 鼠标指针（可选，仅用于文本选择/点击） | 不引入窗口系统 |

### 5.3 明确不做

- ❌ 窗口管理器、合成器、桌面隐喻、多窗口叠加
- ❌ X11 / Wayland 兼容层、GPU 驱动
- ❌ 给图形模式做一套"独立应用体系"——它承载的应用就是 shell 与 CE/native 命令行程序
- ❌ 把 `gfx_*` 变成"应用画窗口"的 API——它是"应用画得更自由的字符"的 API

**验收**：所有 shell 命令与 TUI 程序在 gfx 后端下行为与 text 后端一致；btop 在 40×12 与高分辨率
下均无 wrap；不新增任何窗口/合成概念；图形模式下用户看到的仍然只有 shell。

## 6. 工程纪律

1. **每阶段收尾必须实机验证**，禁止以"编译通过"作为完成标准（I2）。
2. **双人格永不同时破坏**：任何改动后，legacy 回归 12/12 + 四探针必须全绿。
3. **ABI 变更走追加**：native syscall 表也采用版本号 + append-only，避免重演 CE 的兼容债。
4. **安全修复清单随阶段携带**（I3），每次合并外部代码都要逐项核对。
5. **外部表现回归是硬指标**（I4/I5）：每个阶段都要对比 shell 命令输出与图形界面，
   不允许"内部升级了但用户得重新学"的情况。
6. **文档滚动更新**：完成一批后，更新本计划对应行的状态（☐→☑）、`docs/历史记录.md` 第二部分，并追加当日 `.workbuddy/memory/` 日志。
7. **构建环境固定**（I6），跨机器先验证工具链。

# CatOS 64 位转型计划：32 位收官 → 64 位接棒

> 定位：本文件是「何时、按什么顺序转入 64 位」的唯一执行计划。
> 上位文档：`PLAN-通用操作系统.md`（双人格总设计、P0–P3 定义）、归档 `archive/设计文档-历史.md`（原 ROADMAP，战略判定）。
> 待办单一入口：`全局待办总表.md`（本文件不复制待办，只定义**顺序与门禁**）。
> 建立：2026-11-23 · 基线：`main` @ `4fec071`，交付版本 v2.78，工作区有 29 个文件未提交改动（约 +1636/−609）。

## 0. 一句话结论

**先收官 32 位，再开 64 位主线**——这个方向成立，但"完全搞定"必须换成一张有界、可勾选的收官清单（§2 的 G1–G4 门禁），并在收官期同时执行两条硬约束（§1.2），否则 32 位会无限膨胀，64 位永远排不上队。

**时间轴（估算）**：32 位收官 2026-11-24 → 2027-01-11（约 7 周）→ 门禁评审 → 64 位 K1–K3 2027-01-11 → 2027-03-29 → **v3.0 = 64 位首发**（缓冲至 2027-04-12）。

## 1. 决策与两条硬约束

### 1.1 为什么串行可行

| 条件 | 现状 | 等级 |
|---|---|---|
| 64 位地基已存在且可验证 | `kernel64/` P0 六项跑通，串口证据 `kernel64/evidence/p0-serial-3840mb-4cpu.log`，验收见 `docs/kernel64-P0-验收报告.md` | confirmed |
| 64 位与 32 位零耦合 | 独立构建（nasm + `gcc -m64` + `ld -m elf_x86_64`）、独立 ISO、独立页面布局 | confirmed |
| 32 位仍能独立发版 | v2.78 已交付，回归脚本 115 个，发布纪律见本文件第三部分 §2.5 | confirmed |
| 双人格策略已定 | legacy CE 冻结为兼容人格，native 走 ELF64 + 数字 syscall（`PLAN §2`） | confirmed |

**串行不等于暂停 64 位**：`kernel64/` 已完成的部分**冻结为资产**，不再开发、只做回归（防止重演"boot64.s 草稿腐坏"）。

### 1.2 两条硬约束（违反即计划失效）

**约束 A：32 位增量预算。** 收官期（W0–W3）只接受四类改动，其余一律进 `64 位 backlog`：

1. P0/P1 缺陷修复（含隔壁 agent 正在做的 bug/性能小优化）
2. 回归失败修复（回归绿率不得下降）
3. 汉化/文案/一致性（`shell.c` 641 处硬编码英文属此类）
4. 构建可复现与工具链（`build.sh` 类）

**约束 B：新增代码必须"64 位可搬"。** 收官期新增/改动遵守：

- 新增内核模块避免新的恒等映射假设（不新增 `phys == virt` 的隐式依赖）
- 新增 syscall 槽优先**描述符式**（指针打包进结构体，如 `gfx_rect_t`/`gfx_blit_t`），避免再堆裸指针参数
- 用户态新功能优先走 `pkg`（`.catpkg`），不改 CE ABI；确需加槽则三处同序同步（`ce_abi.h`/`ce.h`/`task.c`）
- 不新增 32 位专用汇编（`cpu.s` 类）；必须新增时同步在 `kernel64/` 留 TODO 行

> 理由：现状 54 个 C 文件 / 1.31 MB / 约 3.07 万行，`shell.c` 单文件 332 KB。每延迟一个季度，K2「外观回归」的搬迁面就多几千行。

## 2. "32 位搞定"的可检验定义（门禁）

**定义**：不是"把所有想法都实现完"，而是**已承诺的功能全部可用、已知 P0/P1 缺陷清零、外部表现回归全绿、文档与代码一致**。新想法不算欠账，一律进 64 位 backlog。

| 门禁 | 判据（可勾选） | 当前状态 |
|---|---|---|
| **G1 功能面** | 第三部分（待办总表）中 A/D/E/F 线 **P0/P1 项全部 ✅ 或有明确"延后到 64 位"的书面决定**；§10「明确不做」清单不再被临时推翻 | 🔶 |
| **G2 质量面** | ① `tests/run_full_regress.sh` 与「12/12 回归 + 四探针」全绿（`PLAN §6.2`）；② `CatOS-内核问题清单.md` 无未决 P0；③ 对抗 R1 剩余 6 项（#188–#193）逐项给出「修」或「延后」结论 | ☐ |
| **G3 工程面** | 干净树 `sh build.sh iso` 一次成功且 ISO 可启动（当前 `build.sh` 有"不更新 ISO / .inc 时间戳"坑，见 §F4）；`test_app_list.py` 守卫绿；核心 8 个探针可无人值守跑 | 🔶 |

**G2 中的 E3 是硬前置**：`SYS_WRITE`/`SYS_PIPE_WRITE`/`SYS_FILE_WRITE` 的裸指针访问必须全部改成 `copy_from_user()` 快照（第三部分 §7 E3）。这条同时是 64 位开内核抢占（K1）的前提——在 32 位收官期还掉它，是最划算的一笔投资。

## 2. 宪法级约束（任何阶段都不得违反）

摘自 `PLAN-通用操作系统.md` §0 与项目长期记忆，所有待办都在此框架内：

1. **CE ABI append-only**：`catos_api_t` / syscall enum 只能往表尾追加，绝不插入/重排，
   否则老 `.ce` 二进制错位崩溃。新槽必须三处同序同步：`ce_abi.h` / `ce.h` / `task.c`
   的 enum + nargs + isr case（血泪教训见 CDE 设计 §5）。
2. **图形模式 = shell 的图形后端**，不是独立 GUI 体系；不做 X11/Wayland 兼容
   （PLAN §5.3）。演进只做 VBE 高分辨率、自由排版、双缓冲、UTF-8、TUI 构件、可选鼠标。
3. **换内部，不换外部**：每个阶段收尾都要过 QEMU 实机回归 + 四探针，外部表现回归对比。
4. **新工具先出原型**：先在命令行/Textual 里写原型、给用户看到效果，再决定是否移植进内核。
5. **发布纪律**：每轮实质工作后自动 commit + push；新版本复制
   `catos-vX.XX.iso` + `kernel-vX.XX.bin`，VMX 指向新 ISO（虚拟机运行时不改）。
6. **字体基线**：CE 字体以本地 IBM VGA 8x16 ROM 版 `font_ascii.inc` 为准，
   不回退到 8x8 拉伸版。

# kernel64 P0 验收报告（C-P0.1 ~ C-P0.6）

日期：2026-11-23
范围：本文件第三部分 §5.1（原 `全局待办总表.md` 线 C / 通用 OS 战略 P0 — 64 位地基）

## 结论

P0 六项全部落地并跑通，具备"GRUB → long mode → C 内核 → ring3 ELF64 → syscall 返回 → REPL"
的完整闭环。原先 `kernel64/` 只有一份半成品 `boot/boot64.s` 草稿（GDT 写字节错乱、页表循环不
写值、STAR 构造冗余），本次按"可验证优先"整树重写。

验收命令与现场：

```
qemu-system-x86_64 -cdrom build/catos64.iso -m 3840 -smp 4 -serial stdio -display none -no-reboot
```

## 逐项交付

| 项 | 实现 | 验证点 |
|----|------|--------|
| C-P0.1 | `boot/boot32.s`：multiboot 头、清 bss、存 mb_info、建表、`EFER.LME`、`CR0.PG`、`lgdt`、far jmp `0x08:_k64` | 串口 banner 打出 multiboot flags/mem_upper/mmap_len |
| C-P0.2 | PML4[0]→PDPT（US 宽松 0x07），PDPT[0]→identity PD（512×2 MiB，0–1 GiB），PDPT[1]→用户 PD | 内核在 VA=PA 下运行；用户窗口 0x40000000 可进 |
| C-P0.3 | `src/pmm64.c`：1 bit/4 KiB、4 GiB 位图、按 mmap type=1 释放、保留 low 1 MiB/内核镜像/mb 结构；`pmm_alloc`、`pmm_alloc_2m` | 3840 MB：used=262483、free=786093 与 mem_upper 一致 |
| C-P0.4 | `src/idt64.c` + `boot/isr64.s` + `src/serial.c`：256 项 IDT、异常 0–31（两条路径：无错误码补 0 / 带错误码）、IRQ 32–47、`int 0x80` DPL3、TSS(rsp0)、PIC/PIT 1 kHz、PANIC 打印 vec/err/rip | PIT 计数增长；故意错误的访问打出 `PANIC: exception vec=14 err=... rip=...` |
| C-P0.5 | `src/sys64.c` + `boot/isr64.s:syscall_entry`：STAR=(0x20<<48)\|(0x08<<32)、LSTAR=syscall_entry、SFMASK=0、EFER.SCE=1；`sysret` 回环 3 | demo 里 `syscall` 写一行、再用 `int 0x80` 写一行证明已回到 ring3 |
| C-P0.6 | `src/elf64.c` + `boot/demo_inc.s`（`incbin build/hello.elf`）+ `demo/hello.s`/`demo/hello.ld` | ELF64 PT_LOAD 拷贝到用户物理帧、`enter_user` iretq 进 ring3、exit 后回 `catos64>` |

## 关键设计取舍

1. **不用 higher-half**：原 `k64.h` 草稿写 VA `0xFFFF80000000`，但 P0 阶段没有任何收益，反而要
   维护两份映射并让 C 代码区分 `KPHYS`/`VA`。改为 identity 0–1 GiB + 一个 user 窗口，寄存器级
   行为可预测。higher-half 留到 P1 引入 VMA/物理内存分区时再迁移（届时只改 trampoline 与链接基址）。
2. **用户窗口用 PMM 分配的 2 MiB 帧，不写死物理地址**：第一版写死 `0x3E000000`（≥1 GiB 才有 RAM），
   `-m 512` 下页表有值但物理页根本不存在，ring3 一执行就 `#PF err=0x5`。现在 `pmm_alloc_2m()` 在
   `user_window_init()` 里取帧并回填 `pd_user_t[0]`/`pd_user_t[1]`，再重载 CR3。
3. **先 `int 0x80` 后 `syscall`**：`int 0x80` 由中断门自动切 TSS.RSP0，能先把 ring3 通路跑通；
   `syscall` 不切栈，需手写 `kernel_rsp_save` 栈切换 + `sysret` 返回，两条路径都保留。

## 踩坑记录（都在本次修复）

| 症状 | 根因 | 修复 |
|------|------|------|
| long mode 后立刻 `#UD`/triple fault，QEMU 报 `CR4=0x20` | GRUB 32 位环境没开 SSE，且 `CR0.EM/TS` 未清，C 代码里 `movq %rax,%xmm7` 直接 #UD | `CR4 |= PAE|OSFXSR|OSXMMEXCPT`，`CR0 &= ~(EM|TS)` 且 `|= MP`，且**先 idt 后 pmm**，否则异常被静默成 triple fault |
| `mb_info` 里的 mmap 地址失效 | 存 `mb_info` 早于清 bss，被 `rep stosd` 冲掉 | 清完 bss 再 `mov [mb_info], ebx` |
| PMM 统计循环"卡死"，每秒只推进几十帧 | IRQ0 桩只 `push 0`、`call` 后直接 `iretq`，被中断的 `rax/rcx/rdx` 全被 C 函数冲掉，循环状态被持续破坏 | IRQ/ISR/`int 0x80` 桩统一 15 个 GPR 全保存（`PUSHREGS/POPREGS`） |
| ring3 第一条指令 `#PF err=0x5` | ①用户窗口写死 PA 超出实际 RAM；②PML4/PDPT 中间层没置 U/S | ①改 PMM 分配（见上）；②中间层 `0x07`，叶子 `0x87` |
| `sysret` 后 `#GP err=0x30` | `SYSRET` 规定 CS=`STAR[63:48]+16`、SS=`+8`，而 GDT 里 ucode 在 udata 前面 | GDT 重排为 `0x28 udata(DPL3)`、`0x30 ucode(DPL3)`，`STAR[63:48]=0x20`，选择子 0x2B/0x33 |
| ELF 段被判定 "outside user window" | 用 `ld -Ttext=0x40000000` 起步，段被页对齐拉低 | 改用 `demo/hello.ld`（`. = 0x40000000`），并把段校验放宽为 `[0x40000000, +4 MiB)` |
| NASM 把 `sysretq` 当标签 | NASM 版本不支持该助记符，只报 "label alone on a line" 警告，代码静默变成 fall-through | 写成 `db 0x48,0x0F,0x07` |

## 已知边界（不属 P0 验收范围）

- **SMP 只跑 BSP**：`-smp 4` 下其余 3 个 AP 停在 real mode，没做 INIT/SIPI、AP 的 GDT/IDT/栈。
- **物理内存上限 4 GiB**：位图按 4 GiB 静态开（128 KiB），>4 GiB 需扩到动态位图/分段池。
- **无 2 MiB 大页分配器**，无 NUMA，无 per-CPU 缓存。
- **纯 identity 映射**：超过 1 GiB 的 RAM 目前不可达（P0 只用 low 1 GiB）。
- **旧树回归 12/12 未跑**：本轮未在 `kernel_v25` 上执行回归脚本（相关改动属于一天级任务，由并行子代理处理）。
- **无中断优先级/软中断**：IRQ 全在 PIC 下、只开 IRQ0；APIC 属 P1（C-P1.5）。
