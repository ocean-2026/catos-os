# CatOS 通用化路线图（ROADMAP）

> 定位：从"hobby 教学内核"向**可通用命令行操作系统**挺进。
> 本文是 2026-11-10 架构评估（六条劣根性）之后的行动纲领，随每一轮交付滚动更新。
> 问题级明细见 `docs/CatOS-内核问题清单.md`，本轮完成情况见 `docs/PROGRESS.md`。

## 一、总纲

CatOS 已具备通用 OS 的**骨架要件**：多任务 + FAT32 文件系统 + 管道/重定向 + 网络栈 +
SB16 音频 + 24bpp 真彩图形 + 多用户/能力权限。当前的主要差距不在"缺功能"，而在
**架构假设**——以下按"是否动设计假设"分三档推进。

## 二、已消除的劣根性（增量修复，已完成）

| 劣根性 | 解法 | 交付 |
|---|---|---|
| syscall 边界裸解引用（ring3 可让内核 #PF 停机） | `copy_from_user()` 内核快照统一化，#78/#86 全闭环 | `62cd529` |
| 崩溃即 halt、零诊断 | `diag.c` 致命故障记录 + `faultinfo` + `panic()` + `fsck` | `62cd529` (#87/#88) |
| 应用清单双处硬编码 | `build/apps.list` 单一来源 + 守卫测试 | `62cd529` (#89) |
| 应用绑死内核镜像 | 预装 FAT32 磁盘为应用真实来源，内嵌降级为 fallback | `4fb3318` (#90) |
| 单用户 + 写死权限表 | `/etc/passwd` + `/etc/acl` + 7 位能力位，内核分发处强制 | `febc9b8` (#91) |
| 用户态应用被迫篡改中断控制器（屏蔽 IRQ1 + 直读 PS/2 端口轮询按键） | CE ABI v2.14 追加 slot 64 `pollkey()` 非阻塞按键，ring0 hack 全部退役 | `443c067` (#92) |
| 基础文件操作缺位、依赖 134 KB 用户态工具箱 | shell 内置 `cat`/`rm`/`cp`/`mv`（ACL 权限）；ot 去重后收编为 `/bin/ocntools.ce` | `443c067` (#93/#94) |

## 三、判定为重写级、当前不做（诚实清单）

这些不是"没做"，是**评估过、算过代价、明确不做**：

1. **取消恒等映射 / 独立用户地址空间**：12+ 文件、147 处全局状态依赖
   "内核=物理内存"假设；真实收益在 SMP 与防 ring3 探测内核布局，教学内核阶段不值。
2. **SMP / 内核抢占**：`intr.c` 硬编码 IRQ、`g_in_syscall` 非抢占保证遍布 syscall。
   抢占化会连带推翻 #86 靠非抢占保住的 static 缓冲安全（见清单 14.2）。
3. **内存动态化**（COW / 换出 / 解除 512 KiB 堆上限）：`frame_alloc` 固定 64 MiB、
   每 arena 单页表，重构级；最危险的前置（#86 裸指针）已消掉。

## 四、下一批目标（增量可做，按优先级）

### P1 — 通用性补课
- **spawn 执行权限检查**：`task_spawn_ce` 尚不查 `PERM_EXEC`（#91 遗留），补上。
- **多组支持**：`task_t` 只有单 gid，用户库扩展 supplementary groups。
- **口令哈希升级**：djb2 仅防窥视；至少换带盐的多次迭代哈希，明示非密码学边界。
- **shell 作业控制**：后台 `&` / `jobs` / `fg`（任务框架已支持 spawn+wait，只差 shell 层）。

### P2 — 生态与应用层
- **用户态 libc 雏形**：把 `ce_stub.c` + api 包装抽成 `libc.a`，应用不再各写一遍 boilerplate。
- **自举环闭环**：`cc_self.c`（阶段 1-3 编译器）在 CatOS 内编译自身 → 迭代改进，
  这是"通用 OS + 自承载工具链"的标志性里程碑。
- **长文件名（LFN）**：当前 8.3 名是 FAT 兼容性短板，读侧先支持。
- **目录递归操作**：`cat`/`rm`/`cp`/`mv` 已随 v2.14 落地（#93），补 `cp -r`、`mkdir -p`
  类递归/批量形态与目录删除。

### P3 — 视投入而定的中程项
- **键盘布局 / 编码**：拼音 IME 已有（render-split 合流产物），补 UTF-8 输出一致化。
- **简单守护进程框架**：常驻任务 + 事件等待原语（当前 `delay()` 轮询是唯一手段）。
- **安装器**：`mkdisk.py` 已能在宿主生成预装盘，包一层"系统安装"故事（选盘、设 root 口令）。

## 五、里程碑判定标准

"可通用命令行 OS"达成的可检验定义（当前 ✅/❌）：

| 判据 | 状态 |
|---|---|
| 多用户 + 细粒度权限，root 初始用户 | ✅ #91 |
| 应用可独立于内核镜像分发/更新 | ✅ #90 |
| 崩溃可归因（诊断）、文件系统可自检 | ✅ #87/#88 |
| 用户程序无法让内核停机（已知类别） | ✅ #78/#86 |
| 图形 / 音频 / 网络 / 自带编译器 | ✅ |

# CatOS vs 通用操作系统差距分析（2026-11-17）

> 基线：HEAD `6cf1ff6`（v2.45），32 位 x86 单内核，QEMU/i386，GRUB multiboot，FAT32。
> 本文档为**纯调研交付**：只列差距、现状定位、通用 OS 做法、评级与今夜可行性，不含内核/应用代码改动。
> 承接文档：`docs/pe-dynamic-linking-design.md`（动态链接 P1 设计）、`docs/ROADMAP-通用操作系统.md`（三档路线图）、`docs/CatOS-内核问题清单.md`（#128~#152 历史项）。

## 0. 口径与评级说明

- **现状**：引用仓库内源码文件 / 函数名 / 行号区间，均已在基线 HEAD 上核实；与任务初判不一致处按源码实际记录。
- **差距评级**：
  - **高**：通用 OS 标配、直接影响可用性/兼容性；
  - **中**：通用 OS 标配但 CatOS 已有部分等价物，缺的是完整性或标准合规；
  - **低**：边角体验 / 加固项。
- **今夜可行性标注**：
  - **可增量**：现有架构内可小步落地，风险可控；
  - **需设计文档级重写**：动核心假设，需先出设计文档再排期；
  - **暂缓（deferred）**：评估过代价，本轮明确不开工。
- 每条目附「今夜预估工作量 / 主要风险」，供父代理按清单派工。

## 1. 调研方法

- 外部基线：FAT VFAT LFN 规范、POSIX 作业控制与信号模型、口令哈希基线（PBKDF2/bcrypt/scrypt/OWASP）、通用 TUI 组件模型。

## 2. 增量候选差距项（必查清单）

### 2.1 FAT LFN 长文件名（读侧优先）

**现状（基线 `6cf1ff6` 已核实）**

- 读侧（v2.18）：`src/fat.c` 中 `lfn_acc_reset()` / `lfn_acc_feed()`（520–545 行）按序号聚合前置 LFN 条目，`lfn_of_short()`（549–552 行）用别名校验和匹配；目录列举 `fat_list_dir()`（约 870 行）优先返回长名；`LFN_MAX_CHARS 240`（446 行）。
- 写侧：`dir_write_lfn()`（723–801 行）生成 `BODY~N.EXT` 别名并写入 LFN run；`lfn_checksum()`（448 行）按 8.3 别名计算校验和；`dir_write_lfn()` 在目录簇内找连续空闲窗口（719–743 行）。
- 删除：`fat_delete_name()`（817–866 行）把短条目标 `0xE5`，并按校验和回收前置的同 checksum `0x0F` LFN 条目。
- **已核实缺口与待复核边界**：
  1. 无原生 rename 路径：shell `mv` 实现为 copy + delete（`src/shell.c` 2792–2798 行）；改名走新建 LFN run + 删除旧条目，跨目录移动、长名覆盖、删除失败时旧别名链残留等语义未测。
  2. 别名碰撞规则未与 Windows 短名生成规则核对（前 6 字符大写 + `~N` 递增）；别名编号耗尽、8.3 重名冲突时的行为未知。
  3. 写侧跨目录簇的 LFN run 拼接、满目录下连续窗口失败路径未见明确错误处理。
  4. 8.3 条目的 lcase 字节（offset 12）未写；与 NT/Windows 互操作时短名大小写语义可能丢失。
  5. 长名上限 `LFN_MAX_CHARS 240` 与规范 255 码元有差距；文件名非法字符集（`/ \ : * ? " < > |`）过滤未见实现。
  6. 末槽 `0x0000` 终止符与未用字符 `0xFFFF` 填充的写侧细节需对照规范复核。

**通用 OS 做法（VFAT 规范要点）**

- 长名按每槽 13 个 UCS-2 字符拆分；LFN 条目属性字节恒为 `0x0F`（只读+隐藏+系统+卷标），起始簇字段恒为 0；槽位逆序存放，末槽序号 `OR 0x40`；槽内未用字符填 `0xFFFF`，末尾补 `0x0000`。
- 每槽携带 8.3 别名校验和：`sum = (((sum&1)<<7)|((sum&0xfe)>>1)) + name[i]`（遍历 11 字节短名）。
- 别名生成：大写前 6 字符 + `~1`，冲突递增；长名最多 255 个 UTF-16 码元。
- 旧 DOS 工具只识别 8.3 别名、忽略 LFN 条目；非 VFAT 系统上拷贝会丢失长名。
- 参考：Linux kernel `Documentation/filesystems/vfat.txt`；Microsoft FastFAT（The FAT File System）；FAT directory entry 结构说明（tc.gts3.org fat-structs.pdf）。

**差距评级**：中（读侧主路径已通，缺口集中在写侧健壮性与互操作细节）。

**今夜可行性**：**可增量**。第一批做读侧兼容核对、非法字符过滤、别名碰撞与目录满失败路径的单测；原生 rename 路径属小设计，排第二批。
**工作量 / 风险**：小~中；风险低，纯 fs 层改动，不动 CE ABI。

### 2.2 动态链接（承接 pe-dynamic-linking-design.md）

**现状（已核实）**

- CE01 flat 镜像：20 字节头（magic `CE01`、entry、bss_size、api_offset、image_size）+ 扁平代码/数据，固定加载到 `USER_IMAGE_BASE = 0x2000000`；内核在 `USER_VSYSCALL = 0x2080000` 建 vsyscall 页，函数指针表 `VS_TABLE = 0x2080800`，槽位 append-only（现 65+ 槽），老二进制不受影响。
- ELF32 轨道：`spawn_load_elf()`（`src/task.c:1933`）支持 PIE + ASLR，段映射进扩展竞技场 `USER_EXT_BASE 0x2400000` ~ `USER_EXT_END 0x2800000`。
- PE32 轨道：`spawn_load_pe()`（`src/task.c:2086`）只解析 DOS header → PE sig → COFF → Optional header → section headers → entry point；**导入表 / 导出表 / 重定位表一律忽略**（问题清单 #130）；`tests/mkpe.py` 离线把 PE32 翻译成 CE01 flat。
- 不存在的机制：跨任务共享只读代码段（页帧按任务分配）、模块表 / 引用计数 / 卸载路径、运行时链接器（ld.so 等价物）、符号名/序号解析。
- 承接设计：`docs/pe-dynamic-linking-design.md` 已评估三条路线——路线 1 离线/装载期静态重定位（推荐，延续 P1 方向）；路线 2 内核装载期重定位 + 导入绑定 vsyscall 槽；路线 3 用户态动态链接器。

**通用 OS 做法**

- 装载器解析 Import Directory Table / Export Directory / `.reloc` 基址重定位块；GOT/PLT 绑定到真实函数地址；只读 `.text` 被多任务共享映射；模块带引用计数与卸载路径；动态链接器按依赖链递归装载。

**差距评级**：中（教学内核阶段非阻塞，但是生态复用外部二进制的主要天花板）。

**今夜可行性**：**需设计文档级重写**（运行时动态链接）；其中**路线 1 离线重定位可增量**：在 `mkpe.py`（或内核装载器）补 PE `.reloc` 条目（`IMAGE_REL_BASED_HIGHLOW`）按实际加载基址逐条修正绝对引用，外部调用直接绑定 vsyscall 槽位。共享页、模块生命周期、运行时链接器 deferred。
**工作量 / 风险**：离线工具侧小；内核侧重定位循环中；共享页与模块管理触及内存模型，属重写前置。

### 2.3 守护进程框架

**现状（已核实）**

- 任务状态机：`T_UNUSED / T_READY / T_RUNNING / T_SLEEPING / T_WAIT_KB / T_WAIT_CHILD / T_ZOMBIE`（`include/task.h:30–37`）。
- 唤醒源只有三类：timer tick（`task_sleep_ticks()`，`src/task.c:259`；`SYS_DELAY` 1219 行）、子进程退出（`T_WAIT_CHILD`）、按键（`T_WAIT_KB`）。
- 后台常驻任务靠 shell `&` + `delay()` 轮询（范例 `extapp/spinner.c`）；**无通用事件等待原语**（信号量 / 事件标志 / 条件等待队列）、无信号分发、无 daemonize / 会话脱离、无开机自启服务清单。
- 后台任务输出由 shell 捕获为日志，经 `jobs` / `log TID` 查看（`src/shell.c:1590–1643`）。

**通用 OS 做法**

- daemonize：fork + `setsid()` 脱离控制终端、重定向 stdio、切换 cwd、重置 umask；init / systemd 以单元为单位管理常驻服务；事件循环基于 poll/epoll 或事件队列 + 阻塞唤醒原语；信号（SIGHUP 重载、SIGTERM 退出）异步投递到进程。

**差距评级**：中。

**今夜可行性**：**可增量**（轻量版）：内核补一个通用事件等待/唤醒原语（或最小信号量槽），ABI 加 daemon 标记与自启清单文件；完整会话模型与信号分发需与 2.4 作业控制一起设计。
**工作量 / 风险**：中；风险点是阻塞原语与现有非抢占假设、#86 static 缓冲安全模型的交互，需回归调度与后台任务测试。

### 2.4 Shell 作业控制（`&` / `jobs` / `fg` / `bg`）

**现状（已核实）**

- 已有：尾 `&` 后台解析（`src/shell.c:4272–4276`）；`jobs` 内建 `cmd_jobs()`（1603 行，遍历 `t->bg_mode` 任务）；`log TID`（1634 行，查看后台任务捕获输出）；`kill TID`（4221–4229 行，无条件终止，不带信号号）。
- **缺口**：
  1. 无 `fg` / `bg` 内建：后台任务无法拉回前台，被停止的任务无法继续。
  2. 无进程组 / 作业组概念：`task_t` 无 pgid；管道三段（shell.c:1399 起）各自独立调度，键盘中断无法打到整组。
  3. 无信号抽象：CE ABI 无 signal 槽；无 SIGTSTP / SIGCONT / SIGINT / SIGCHLD；Ctrl-Z 挂起、Ctrl-C 组终止均未实现。
  4. 无前台进程组归属：终端驱动不区分前台/后台，后台任务读终端不会被停止（无 SIGTTIN / SIGTTOU 机制）。
  5. 子进程状态只区分退出（`T_WAIT_CHILD` / `T_ZOMBIE`），无 stopped 状态；`wait` 无 `WUNTRACED` 等价物。

**通用 OS 做法（POSIX）**

- 会话（session）+ 控制终端 + 前台进程组；`setpgid()` / `tcsetpgrp()`；每条管道归属一个作业组；键盘信号 SIGINT / SIGTSTP / SIGCONT / SIGTTIN / SIGTTOU / SIGCHLD；`waitpid(WUNTRACED)` 感知 stopped 子进程。
- shell 维护作业表：job id、pgid、PID 列表、状态（running fg / running bg / stopped / done）、命令行；`fg %n` / `bg %n` / `jobs` / `kill %n`；会话退出时向作业组投递 SIGHUP。
- 参考：POSIX XBD §3 Job Control；Bash Reference Manual §7.1 Job Control Basics；VT CS3214 Job Control 讲义。

**差距评级**：中（已有后台雏形，缺的是信号与进程组模型）。

**今夜可行性**：**可增量**（第一批）：`fg` / `bg` 内建 + task 增加 pgid + 最小信号枚举（SIGCONT / SIGTERM / SIGTSTP）；完整 POSIX 作业控制（终端归属、SIGTTIN/SIGTTOU、SIGCHLD 通知）属设计级。
**工作量 / 风险**：中；风险：与调度器、非抢占安全模型耦合，必须回归管道、后台、`jobs/log` 既有测试。

### 2.5 口令哈希升级

> 注意：任务初判为"现在是 djb2 单轮"，源码核实后**现状已在 v2.22 升级过一轮**，本节按源码实际记录。

**现状（已核实，`src/user.c`）**

- legacy djb2 单轮：`user_hash_pw()`（62–67 行）仅保留用于校验旧 `/etc/passwd` 记录，校验通过后原地升级。
- v2.22 方案：`pw_hash_salted()`（78–89 行）FNV-1a 混合 8192 轮，每条记录独立随机盐；记录格式 `$S$<salt8hex>$<digest8hex>`（119–130 行）；校验函数（143–151 行）识别 `$S$` 前缀，旧 djb2 记录验证成功即升级落盘。
- **剩余弱点**：
  1. 摘要仅 32 位（uint32）：离线猜测空间 2^32；8192 轮虽抬高单次猜测成本，但无内存硬度，GPU/ASIC 可并行暴力；源码注释已明示非密码学边界。
  2. 盐熵来源为 timer_ticks × 乘数 + 记录地址（119–122 行），熵源弱于独立 RNG；盐仅 32 位。
  3. 算法标签仅半前缀（`$S$`），迭代参数不可配置；无 pepper；无按新方案 rehash 的迁移触发点（除登录成功路径外）。

**通用 OS 基线（OWASP 2025/2026）**

- 首选 Argon2id：m=19 MiB、t=2、p=1（等价配置 46 MiB / t=1）；次选 scrypt N=2^17、r=8、p=1；bcrypt cost ≥10（仅 legacy）；FIPS 场景 PBKDF2-HMAC-SHA256 ≥600,000 轮。
- 每口令唯一随机盐 ≥128 bit；慢且内存硬；算法标签随记录存储；登录成功时按新方案 rehash 迁移旧记录。
- 参考：OWASP Cheat Sheet Series — Password Storage。

**差距评级**：中（已脱离"明文 / djb2 防窥视"档，但距现代慢哈希基线差距明显）。

**今夜可行性**：**可增量**：摘要宽度扩到 128/256 bit、上调迭代轮数、盐接更强熵源；Argon2/scrypt 等内存硬算法在 32 位小内存内核属设计级，今夜不引入。
**工作量 / 风险**：小~中；风险：必须保留旧记录兼容升级路径；哈希耗时需控制在交互登录时延内。

### 2.6 用户态 libc.a 静态库雏形

**现状（已核实）**

- `extapp/ce_stub.c`（20 行）仅提供 `__chkstk_ms()` 空桩（MinGW 栈探测消除）；其余 libgcc 辅助未收编。
- 每个应用各自定义 `__ce_api` 槽并手写 vsyscall 包装（范例 `extapp/spinner.c` 开头：`catos_api_t *__ce_api __attribute__((section(".ce_api"))) = (catos_api_t *)0;`）；字符串 / 内存 / 格式化等辅助函数走 vsyscall 或各 app 自行实现。
- 无静态归档库（`.a`）、无统一应用头文件样板、无独立启动代码（`ce_main` 由链接脚本 `extapp/ce.ld` 定位到镜像偏移 0）。

**通用 OS 做法**

- libc.a 包含启动样板（crt0）、系统调用包装、libgcc 桩、字符串/内存/格式化等纯用户态函数；应用链接时归档并入；头文件单一来源；ABI 变更只改库不改各应用。

**差距评级**：中。

**今夜可行性**：**可增量**。先抽 `ce_app.c` / `ce_app.h`：API 槽初始化 + 常用包装（write/print_int/atoi/delay 等）与通用字符串/内存函数；第一步以源码并入方式落地，暂不做 ar 归档；归档格式与链接脚本改造为后续小设计。
**工作量 / 风险**：小；风险低，纯用户态构建侧，不触内核。

### 2.7 递归文件操作：`cp -r` 与 `mkdir -p`

**现状（已核实）**

- `mkdir -p`：`cmd_mkdir_p()`（`src/shell.c:1051–1087`）逐段创建，错误码映射 `FS_ERR_NOENT / NOTDIR / EXIST / INVAL / FULL`。
- 递归助手（v2.24，2616–2656 行）：`rm -r` / `cp -r`，深度受限防栈溢出；目录复制走 `fs_mkdir(dst)`（2656 行）。
- **缺口**：
  1. `cp -r` 合并/覆盖语义、权限位与时间戳保留；目标目录已存在时的路径拼接规则。
  2. 空目录删除 / `rmdir` 内建；长路径深度上限（与 #151 同源：shell 栈与静态缓冲）。
  3. 递归列举受 `fs_enum_entries` 24 槽枚举限制（#151 遗留 L2/L3）。

**通用 OS 做法**：`cp -r` 递归复制目录树并保留 mode/owner/mtime；`mkdir -p` 幂等、已存在不报错；`rmdir` 仅删空目录；路径先规范化再逐段操作。

**差距评级**：低~中。

**今夜可行性**：**可增量**：语义补齐与错误提示先行；条目收集缓冲改堆上 / 大静态缓冲属 #151 前置，不阻塞本批。
**工作量 / 风险**：小；风险低。

### 2.8 spawn 执行权限检查

**现状（已核实，主路径已闭环）**

- v2.15 / #99：`task_spawn_ce()`（`src/task.c:2360`）装载前统一闸口——`acl_lookup()` 查 0111 执行位（2380–2388 行，全无执行位直接 -13），`fs_perm_check(path, uid, gid, PERM_EXEC)`（2397 行）；CE / ELF / PE 三轨共用此闸口（2461 / 2469 行）；拒绝返回 -13 EACCES（与其他 syscall 拒绝码一致）。
- 残留边角：ACL 缺省条目（`acl_default()`）执行位播种策略；root bypass 语义核对；无文件能力（file capabilities）概念——CatOS 用用户侧 caps 位表达特权。

**通用 OS 做法**：x 位 + 文件能力（capabilities）+ 挂载 noexec；执行前校验进程凭据对目标路径的执行权限。

**差距评级**：低（主路径已闭环，本项主要是补测试用例与边角核对）。

**今夜可行性**：**可增量**（仅补测试与边角核对，无需新机制）。

### 2.9 多用户组支持（supplementary groups）

**现状（已核实）**

- `task_t.gid` 单值（`include/task.h:48`）；`user_rec_t.gid` 单值（`include/user.h:48`）；`/etc/passwd` 单行单 gid 字段（`src/user.c:257–262` 保存、326 行解析）；`/etc/acl` 单 gid（`user.h:68`，`acl_lookup()` 356 行）；`fs_perm_check()` 只比对一个 gid（484 行，12-bit unix 位布局）。
- 无 group 数据库（`/etc/group` 等价物）、无 supplementary groups 列表、无 `newgrp` / 组切换内建。

**通用 OS 做法**：主组 + 附加组列表；进程凭据携带 gid + `ngroups[]`；组权限位匹配任一附加组即放行；`/etc/group` 维护组名 / GID / 成员列表；`newgrp` 切换主组。

**差距评级**：中（教学内核单组可跑，多用户协作与组共享目录场景受限）。

**今夜可行性**：**可增量**（小设计级，非重写）：`/etc/passwd` 追加附加组字段或独立 `/etc/group`；task 凭据带组数组；`fs_perm_check` 遍历组列表。需保证老 passwd/acl 记录向后兼容。
**工作量 / 风险**：中；风险：配置格式兼容与权限回归测试。

### 3.1 取消恒等映射 / 独立用户地址空间

**现状**：内核按"内核 = 物理内存"恒等映射运行；12+ 文件、147 处全局状态依赖该假设；#129 恒等映射未按 multiboot mmap 避让 PCI BAR/MMIO 区间。

**设计要点（供后续设计文档展开）**

- 页表分离：每任务独立用户页表，内核镜像高半区映射、用户态不可见；用户镜像基址与现有竞技场（`USER_IMAGE_BASE 0x2000000`、`USER_EXT_BASE 0x2400000`）重排。
- 全局状态清点：把依赖恒等映射的全局指针 / 静态缓冲迁移到显式地址空间对象或 per-任务结构；`copy_from_user()` 快照边界（#78/#86 已落地）可作为用户态解引用的统一闸门复用。
- 映射避让：页表建立时解析 multiboot mmap 表，避开 PCI BAR / MMIO 区间（#129 前置）。
- 前置依赖：3.3 的 VMA / 帧分配抽象；回归面覆盖全部 CE/ELF/PE 三轨装载器。

**deferred 理由**：教学阶段真实收益主要在 SMP 与防 ring3 探测内核布局；改动面 12+ 文件 147 处，回归成本远高于当前阶段收益。

### 3.2 SMP / 内核抢占

**现状**：`intr.c` 硬编码 IRQ；`g_in_syscall` 非抢占保证遍布 syscall；#86 依赖非抢占保证 static 缓冲安全；单 CPU 运行。

**设计要点**

- APIC 中断分发与 per-CPU 中断路由；每 CPU 独立就绪队列与调度器；自旋锁 / 中断屏蔽规则覆盖全部共享数据。
- 内核可抢占点：syscall 边界、长循环、阻塞原语处插入抢占检查；静态缓冲改为 per-CPU 变量或加锁保护（推翻 #86 现有安全假设前必须先完成这步）。
- 前置依赖：3.1 独立地址空间（多 CPU 共享内核态前提）；每 CPU 变量抽象；中断控制器驱动重构。

**deferred 理由**：抢占化连带推翻 #86 靠非抢占保住的 static 缓冲安全模型；单 CPU 教学内核无并行收益，风险/收益不匹配。

### 3.3 内存动态化（COW / 换出 / 解除 512 KiB 堆上限）

**现状**：`frame_alloc` 固定 64 MiB 框架；每 arena 单页表；用户堆上限 512 KiB；`src/vma.c`（261 行）已有 VMA 雏形；#128 第二段 RAM（PCI hole 之上）未枚举。

**设计要点**

- 页帧分配器：位图 / 空闲链表替代固定框架；补 multiboot mmap 表解析枚举全部 RAM（#128）。
- VMA 抽象：进程地址空间按区间描述（已映射 / 已保留 / 权限），支撑动态扩展 arena 与解除堆上限。
- COW：fork / 映射共享页时置只读，写时复制建私有页表项；换出：回收页帧到交换空间（当前 FAT32 盘上留交换区文件/分区）。
- 前置依赖：3.1 独立地址空间；#86 裸指针类别已清零（已完成）是最危险前置。

**deferred 理由**：重构级；在 3.1 落地前排期。最危险的前置（用户态裸解引用让内核停机）已消除。

# PE/EXE 与轻量动态链接在 CatOS 上的可行性评估（P1 设计文档）

> 状态：P1 只落地 PE32 的**静态子集**支持（路径 A 壳层转换入口、路径 B
> 内核直接加载、路径 C 离线翻译工具）。本文评估在此基础上向"轻量动态链接"
> 演进的路线、内核缺口与成本，**不强求实现**。

## 1. 背景与现状

CatOS 是 32 位 x86 单内核（QEMU/i386，GRUB multiboot，FAT32），自有
应用格式 CE01，**没有动态链接**：

- **CE01 flat 镜像**：20 字节头（magic `CE01`、entry、bss_size、api_offset、
  image_size）+ 扁平代码/数据镜像，固定加载到 `USER_IMAGE_BASE = 0x2000000`。
- **系统调用面**：内核在 `USER_VSYSCALL = 0x2080000` 建 vsyscall 页，函数指针表
  `VS_TABLE = 0x2080800`；CE 镜像在 `api_offset` 处留一个 4 字节槽位，加载时内核
  把表指针写进去。槽位 **append-only**（现 65+ 槽），新增能力只在表尾追加，老二进制
  不受影响。
- **ELF32 轨道**：内核已有 `spawn_load_elf()`，支持 PIE + ASLR，段映射进扩展竞技场
  （`USER_EXT_BASE 0x2400000` ~ `USER_EXT_END 0x2800000`）。
- **PE32 轨道（P1 新增）**：`spawn_load_pe()` 只解析 DOS header → PE sig → COFF →
  Optional header → section headers → entry point，把各 section 载入内存并跳转；
  **导入表 / 导出表 / 重定位表一律忽略**。`tests/mkpe.py` 离线把 PE32 翻译成 CE01
  flat 结构。

## 2. 动态链接到底需要什么

一个标准 PE/COFF 可执行文件在有动态链接的环境里，装载与运行依赖以下机制；P1
全部未覆盖：

| 机制 | PE 中的位置 | 作用 | CatOS 现状 |
|---|---|---|---|
| 导入目录 | Import Directory Table（Optional header 数据目录 [1]） | 列出依赖的 DLL 与导入符号（ILT/IFT） | 未解析，直接跳过 |
| 导入查找 | 名称/序号 → 目标 DLL 导出地址 | 把调用点补全为真实函数地址 | 无符号解析、无 DLL 装载 |
| 导出目录 | Export Directory（数据目录 [0]） | 本模块对外暴露的函数/符号表 | 未解析 |
| 基址重定位 | `.reloc` 段（数据目录 [5]） | 镜像未被加载到首选 ImageBase 时，修正绝对地址 | 无重定位引擎；P1 要求 PE 落在用户竞技场内 |
| 共享代码段 | 只读 `.text` 被多任务映射 | 库代码在内存中只存一份 | 内核页帧按任务分配，无跨任务共享页 |
| 模块生命周期 | 装载引用计数、卸载 | 库被多少程序使用、何时释放 | 无模块表、无卸载路径 |
| 动态链接器 | 运行时 `ld.so` 等价物 | 装载依赖、解析符号、修 GOT/PLT | 不存在；无用户态链接器 |

## 3. 三条演进路线评估

### 路线 1：离线/装载期静态重定位（推荐，延续 P1 方向）

**做法**：在 `mkpe.py`（或内核装载器）里完成全部"链接"工作——
1. 解析 PE 的 `.reloc` 基址重定位块；
2. 按实际加载基址（CE 固定基址或 ELF PIE 基址）逐条修正绝对引用；
3. 把外部调用直接绑定到 CatOS vsyscall 表槽位（等价于把 PE 的 `import kernel32`
   之类映射到 CatOS 自有 ABI），产出自包含的 CE01/ELF 镜像。

**优点**：
- 完全贴合现有内核：不需要共享页、符号表、运行时链接器；
- 与 CE01 append-only ABI 一致，外部能力走 `VS_TABLE` 槽位；
- 装载路径简单（现状 `spawn_load_pe` 已能映射/拷贝段）。

**限制**：
- 不支持运行时动态装载新模块；一个程序链接到的库在构建/翻译期就固定；
- 跨程序复用同一份库代码会在每个镜像里各拷一份（空间换复杂度）。

**内核改动量**：小。主要是离线工具侧补重定位解析；内核若要在装载期做重定位，
需补一个 R_386_RELATIVE 等价的基址修正循环（PE `.reloc` 条目类型 `IMAGE_REL_BASED_HIGHLOW`）。

### 路线 2：固定基址的轻量共享模块（中期可选）

**做法**：在用户地址空间预留一块"库区"，每个 CE/PE 库被分配一个固定首选基址；
模块导出符号在构建期静态登记进一张内核/启动期符号表；程序调用库函数时按
编译期就确定的固定地址跳转。内核只需：
- 扩展竞技场映射能力，把库段映射进多个任务的地址空间；
- 维护一张模块/符号登记表（路径 → 基址 → 导出表）；
- 装载程序时把其依赖的库段一并映射进来。

**优点**：
- 比路线 1 省内存（库代码一份）；
- 不需要运行时符号解析（地址构建期固定），实现复杂度可控。

**限制**：
- 地址空间手工分配，库之间不能冲突；基本放弃 ASLR；
- 仍不支持运行时插拔/卸载；
- 跨任务共享只读代码段要求内核页帧引入引用计数与共享映射（见第 4 节缺口）。

**内核改动量**：中。需要模块登记表、库区预留、共享页映射，以及库段的 VMA 标记。

### 路线 3：完整动态链接（暂不具备前提）

**做法**：实现等价于 Linux `ld.so` 的运行时链接器：按需装载依赖 DLL、解析符号、
懒绑定 GOT/PLT、引用计数卸载。

**前置条件（CatOS 当前都不具备）**：
- 跨任务共享只读页（页帧 refcount、页目录项共享映射）；
- 持久化的符号/导出表查询接口；
- 动态链接器的内核装载原语（按路径装载模块、分配模块地址区、返回映射基址）；
- 重定位引擎在运行时对已映射镜像打补丁；
- 模块卸载与依赖引用计数。

**结论**：路线 3 成本最高，且与 CatOS 当前"单用户、扁平地址空间、无共享页"的
内核模型差距最大；在路线 1/2 跑通之前不建议启动。

## 4. 若要做路线 2，内核侧缺口清单

1. **共享只读代码段**：`kzalloc_frame()` 目前按任务独占分配；需要页帧引用计数，
   并允许同一物理帧被多个任务的页表项映射（库 `.text` 只读共享）。
2. **模块地址区表**：在用户竞技场之外登记已装载模块的基址/大小/权限，避免冲突。
3. **符号/导出表查询 syscall**：把 CE 头之外的导出目录（或离线生成的 `.sym` 表）
   暴露给装载器；当前 `catos_api_t` 只覆盖内核服务，不含用户模块符号。
4. **重定位引擎**：PE `.reloc`（HIGHLOW）与 ELF `R_386_RELATIVE` 的基址修正循环；
   P1 的 `spawn_load_pe` 目前直接拷贝原始段，未打补丁。
5. **模块生命周期**：装载引用计数、卸载回收、依赖闭包。
6. **依赖装载顺序**：程序装载前先递归装载其依赖库，再解析导入调用点。

## 5. 建议

- **P1 保持静态子集**：路径 A/B/C 只支持能独立运行、无外部导入、基址落在用户
  竞技场的 32 位 PE；不支持的 PE 返回明确错误码而非崩溃。
- **短期**：把路线 1 做扎实——`mkpe.py` 补 `.reloc` 解析与基址重定位，外部能力
  统一走 vsyscall 表；内核装载器对无法重定位的镜像给出"需离线转换"的提示。
- **中期**：若出现多个程序复用同一库的需求，再评估路线 2 的固定基址库区；先补
  共享页帧与模块登记表。
- **路线 3**：作为远期方向记录，不在 P1/P2 迭代范围内。

## 6. 附：P1 已落地的边界（供后续对照）

- 支持：PE32（magic `0x10b`）、i386（machine `0x14c`）、EXE（非 DLL）、
  首选基址在 `USER_IMAGE_BASE` ~ `USER_EXT_END` 内、段 raw 数据在文件内、
  入口落在已映射段内。
- 忽略：导入表、导出表、资源段、调试信息、TLS、异常目录。
- 拒绝并报错：PE32+（64 位）、DLL、高地址镜像（`>= 0x80000000`）、段数超限、
  原始数据越界、入口不在镜像内、镜像/bss 超过 CE 上限。

# 离线重定位动态链接设计（路线 1 落地详细设计）

> 基线：HEAD `6cf1ff6`（v2.45）。承接 `docs/pe-dynamic-linking-design.md` 路线 1（离线/装载期静态重定位：`mkpe.py` 离线 `.reloc` 重定位 + 外部能力绑定 vsyscall 表）。
> 状态：**设计文档**，不含已落地代码。配套差距分析见 `docs/os-gap-analysis-2026-11-17.md` §2.2。
> 范围约束：本文只设计路线 1；路线 2（固定基址共享模块）、路线 3（完整运行时动态链接）仍 deferred。

## 1. 目标与非目标

### 1.1 目标

1. 让非首选基址加载的 32 位 PE32 EXE 能在 CatOS 用户竞技区内正确运行：解析 `.reloc` 基址重定位块，把镜像内绝对引用按实际加载基址修正。
2. 外部能力调用在**构建/翻译期**静态绑定到 CatOS vsyscall 表槽位（`VS_TABLE = 0x2080800`，append-only ABI），产出自包含的 CE01/ELF 镜像。
3. 保持现有 PE 装载路径闭环：无 `.reloc`、无导入表的旧 PE 行为完全不变；不可重定位/不支持的镜像返回明确错误码，不崩溃。
4. 改造以离线工具侧为主、内核侧最小改动为原则（与 pe-design §3 路线 1「内核改动量小」结论一致）。

### 1.2 非目标（明确 deferred）

- 运行时动态装载新模块、DLL 依赖闭包装载、懒绑定 GOT/PLT、模块卸载与引用计数（路线 3 前置：跨任务共享只读页、符号表查询接口、模块生命周期，均不具备）。
- 跨任务共享同一份库代码（路线 2 固定基址库区）；本路线每个镜像各拷一份库代码，空间换复杂度。
- 导出目录解析、按名称/序号解析外部符号的运行时查表。
- ARM64 / 64 位 PE / 高地址 ImageBase（≥0x80000000）支持；DLL 不作为主目标（沿用 mkpe.py 现有 EXE 约束）。

## 2. 现状基线（源码定位）

- PE 装载器：`src/task.c:2086` `spawn_load_pe()`——解析 DOS header → PE sig → COFF → Optional header → section headers → entry；收集合并段页范围（2134 行附近）；**导入表 / 导出表 / `.reloc` 一律忽略**（问题清单 #130）。
- 地址区：用户竞技场 `USER_IMAGE_BASE 0x2000000` ~ `USER_EXT_END 0x2800000`；ELF PIE 走扩展竞技场 + ASLR；PE 轨道要求镜像落在竞技场首选基址附近。
- 离线翻译：`tests/mkpe.py`——`parse_pe()`（149 行）解析头/段表并拒绝高 ImageBase（181 行）；`pe_to_ce()`（206 行）按段排序拼扁平镜像；约束：EXE 非 DLL、入口落在 flat 镜像偏移 0（#131）。
- vsyscall：`USER_VSYSCALL = 0x2080000`，函数指针表 `VS_TABLE = 0x2080800`；CE 镜像 `api_offset` 处 4 字节槽由装载器写入表指针；槽位 append-only（现 65+）。
- 权限闸口：`task.c:2369–2398` PERM_EXEC 统一闸口（CE/ELF/PE 三轨共用，拒绝返回 -13 EACCES）。
- 畸形用例基建：`tests/review_assets/gen_bad_pe.py`；已有样本 `BADA_LF.EXE / BADMZ.EXE / OVERSEC.EXE / PESAMPLE.EXE / TRUNC_PE.EXE`。

## 3. `.reloc` 段格式（实现依据）

### 3.1 目录与块结构

- 重定位信息由 Optional Header 数据目录 **[5]（IMAGE_DIRECTORY_ENTRY_BASERELOC）** 定位：RVA + 大小。目录为空（size=0）表示镜像已链接到首选基址，无需重定位。
- 重定位由若干连续块（IMAGE_BASE_RELOCATION）组成，每块 8 字节头：
  - `VirtualAddress`（4 字节）：本块覆盖的页 RVA；
  - `SizeOfBlock`（4 字节）：块总字节（含头）；
  - 其后为 `(SizeOfBlock - 8) / 2` 个 16 位条目。
- 条目 16 位：高 4 位类型 `Type`，低 12 位 `Offset`（页内偏移）；条目指向的 32 位位置 RVA = `VirtualAddress + Offset`。

### 3.2 条目类型（本路线只支持其一）

| Type | 名称 | 处理 |
|---|---|---|
| 0 | IMAGE_REL_BASED_ABSOLUTE | 填充对齐，跳过 |
| 3 | IMAGE_REL_BASED_HIGHLOW | **唯一支持**：32 位绝对地址，补丁值 = 原值 − PreferredImageBase + ActualBase |
| 其余（HIGH/LOW/HIGHADJ/SECTION/SECREL/ARM 等） | — | 遇到即标记镜像不可重定位，返回明确错误码 |

### 3.3 修正公式（32 位 x86）

```
delta = ActualLoadBase − PreferredImageBase
for each HIGHLOW entry:
    addr_rva = block.VirtualAddress + entry.Offset
    if addr_rva 落在某已映射段范围内:
        *(uint32_t *)(image + addr_rva) += delta
    else:
        畸形/越界 → 拒绝装载（见 §7）
```

- `PreferredImageBase` 取自 Optional Header ImageBase；`ActualLoadBase` 为本次装载实际基址。
- 若 `ActualLoadBase == PreferredImageBase`，delta=0，可跳过补丁（仅校验条目落在段内）。

## 4. 离线生成流程（`mkpe.py` 改造点，主路径）

> 推荐主路径：**离线完成全部重定位**，产出固定基址 CE01 flat 镜像；内核不承担补丁计算。内核侧补丁循环作为 §5 的兜底，仅用于装载期基址与首选基址不同的 ELF/PE 混合场景。

### 4.1 改造步骤

1. **解析数据目录 [5]**：`parse_pe()` 增加 reloc 目录 RVA/大小字段；解析失败或目录越界按畸形 PE 处理（§7）。
2. **块/条目解析**：遍历块链，抽取 `(Type, RVA)` 列表；ABSOLUTE 跳过；HIGHLOW 保留；其他类型记入 `unsupported_reloc_types`。
3. **段区间校验**：每个条目 RVA 必须落在某段 `[VirtualAddress, VirtualAddress+VirtualSize)` 内；越界即报错，不产出镜像。
4. **离线基址选定与补丁**：
   - 目标 CE01 flat 镜像固定基址（沿用现有 CE 装载约定）；按该基址计算 delta，在翻译后的扁平镜像缓冲内逐条 += delta；
   - 补丁只允许落在可写/数据段与代码段内的绝对地址槽；只读 `.text` 内的 HIGHLOW 条目按 PE 语义同样修正（装载时 `.text` 暂在可写拷贝区，映射后只读）。
5. **导入绑定（vsyscall 静态绑定）**：
   - 解析导入目录 [1]：DLL 名 + ILT/IFT；建立「外部符号名 → CatOS vsyscall 槽位号」映射表（离线维护一张 PE 导出名 ↔ VS_TABLE 槽位对照清单，清单本身 append-only 扩展）；
   - 为每个被引用外部函数生成一个离线桩节（thunk）：跳转到对应 vsyscall 槽位间接调用；镜像内调用点/ IFT 槽改写为桩地址；
   - 未映射到任何 CatOS 槽位的外部符号：翻译失败，输出明确缺失符号清单（不产出自称可用的镜像）。
6. **产物与元数据**：CE01 头保持 20 字节现有布局；若内核需兜底校验，可在扁平镜像尾部追加一张**重定位补丁表**（RVA 列表，不含原值——delta 由装载时基址差推导），格式在 §5.3 定义；无补丁表的旧镜像按现状处理。

### 4.2 `mkpe.py` 新增错误码（PEError 子类/文案）

- `reloc directory out of file`；`reloc block truncated`；`reloc entry out of section`；`unsupported reloc type 0xN`；`unresolved import: <name>`；`high ImageBase unsupported`（沿用现有）。

## 5. 加载期基址重定位（内核侧改动点，兜底路径）

### 5.1 触发条件

`spawn_load_pe()`（`task.c:2086`）在段拷贝完成、镜像定位到实际基址后：
1. 读取翻译产物携带的补丁表（§5.3）；无表 → 走现状（不打补丁，#130 既有行为）。
2. 计算 `delta = ActualLoadBase − PreferredImageBase`；delta=0 仅做区间校验。
3. 逐条应用 HIGHLOW 修正。

### 5.2 内核补丁循环要点

- 补丁在**任务私有可写拷贝区**完成，映射只读权限在补丁之后生效；与现有段收集/合并流程（2134 行附近）衔接。
- 每条目先做段区间边界检查（RVA ∈ 某段内存范围、32 位对齐可读可写），越界即放弃装载并返回错误码，禁止裸解引用（复用 #78/#86 `copy_from_user` 同类边界纪律）。
- 重定位表长度设上限（条目数/字节数双阈值），防止畸形镜像在内核态做大循环；超限拒绝。
- 补丁循环不申请新内存、不引入锁；保持非抢占假设（与 #86 static 缓冲安全模型一致）。

### 5.3 补丁表格式（离线产物尾部，小端）

```
offset 0:  u32 magic 'CPR1'
offset 4:  u32 preferred_image_base
offset 8:  u32 entry_count
offset 12: u32 reserved (0)
followed:  entry_count × u32 rva   (HIGHLOW 条目 RVA；类型已在离线侧归一为 HIGHLOW)
```

- 内核只认 HIGHLOW；离线侧已剔除 ABSOLUTE 与不支持类型。
- 表紧跟扁平镜像数据，长度记入 CE01 扩展元数据；镜像尺寸上限沿用 `PE_MAX_FILE`，不抬高。

### 5.4 与现有 PERM_EXEC 闸口的交互

- 重定位/导入绑定全部发生在 **PERM_EXEC 闸口放行之后**（闸口 `task.c:2369–2398` 先于装载）：无执行权限的镜像不会进入段映射与补丁流程，避免对无权访问文件做内核态解析。
- 闸口错误码保持 -13 EACCES；重定位/格式错误使用独立错误码（沿用现有 -5 坏镜像族，细分 -16  reloc 越界、-17 未解析导入，具体号段在实现时与现有 CE 错误码表对齐，不冲突）。
- root bypass 与 owner/group/other 语义不变。

## 6. 回滚与兼容策略

1. **无 `.reloc` / 无补丁表的旧 PE**：装载路径与现状逐字节一致；内核补丁循环检测到无表即跳过，行为不变（#130 既有约束文档化为返回「需离线转换」提示的场景）。
2. **离线翻译失败不污染原镜像**：`mkpe.py` 任何一步校验失败即非零退出，不写出 `.ce`；磁盘上旧产物保留。
3. **ABI append-only**：vsyscall 槽位只在表尾追加；新增映射所需槽位走现有 CE ABI 追加流程，老二进制不受影响。
4. **灰度开关**：内核侧补丁循环可加编译期/运行期开关（默认开）；出问题时回退到「无补丁表即不补丁」的现状路径，无需回滚工具链。
5. **旧样本回归**：`tests/review_assets/` 既有 PE 样本必须在改造后全部通过原有用例；新增用例不改变旧样本期望输出。
6. **文档回滚**：本文档与 pe-dynamic-linking-design.md 路线 1 段落对应；若路线 1 落地受阻，退回 P1 静态子集约束（只支持基址落在竞技场、无外部导入的 PE）。

## 7. 测试方案

### 7.1 正常路径

- 首选基址 = 实际基址：delta=0，补丁表存在但不改动数值；镜像 entry 正常跳转。
- 非首选基址：手工构造含 HIGHLOW 绝对引用（全局指针/跳转表）的样例 PE，离线补丁后上屏/调用结果与宿主预期一致。
- 导入绑定：样例调用 2~3 个已映射 vsyscall 槽位（如 write/delay/print_int），输出与原生 CE 应用一致。
- 往返：mkpe.py 翻译 → 内核装载 → 运行；`ps`/退出码/wait 返回值正常。

### 7.2 恶意 / 畸形 PE 用例（扩展 `gen_bad_pe.py`）

| 用例 | 构造 | 期望 |
|---|---|---|
| 截断的 reloc 目录 | 目录 RVA/大小指向文件尾之外 | 拒绝装载，明确错误码，不 panic |
| 块头截断 | 块大小超过剩余文件 | 拒绝 |
| 条目 RVA 越界段 | 条目 RVA 落在所有段之外 | 拒绝（-16 族） |
| 不支持的重定位类型 | Type=4/5/10 等 | 拒绝并报 unsupported type |
| 超大条目数 | 条目数超内核阈值 | 拒绝，不进入长循环 |
| 重复/重叠块 | 同页两块重叠 | 离线侧告警拒绝；内核侧去重或拒绝 |
| 未解析导入 | 引用无对照清单的 DLL/函数 | 翻译失败，列出缺失符号 |
| 既有坏样本 | BADMZ / BADA_LF / OVERSEC / TRUNC_PE | 保持现有拒绝行为不回归 |
| 镜像尺寸超限 | 超 `PE_MAX_FILE` | 沿用现有 -3/-5 拒绝 |

### 7.3 回归

- 现有 PE/ELF/CE 三轨装载用例全绿；管道/后台/权限闸口（PERM_EXEC -13）用例不回归。
- 离线工具单测：块/条目解析、delta 计算、RVA 校验、桩节生成，覆盖 §7.2 各类畸形输入。
- 真机/QEMU 冒烟：翻译产物启动、调用 vsyscall、退出回收（ZOMBIE 被 reaper 回收）。

## 8. 风险清单

| 风险 | 等级 | 缓解 |
|---|---|---|
| 补丁循环在内核态越界解引用 → 停机 | 高 | 条目区间校验前置；边界检查复用 #78/#86 纪律；阈值限长；畸形用例全覆盖 |
| 导入映射清单不全，外部能力绑不上 | 中 | 离线侧拒绝并列出缺失符号；清单 append-only 逐步补槽 |
| 离线补丁与内核兜底补丁两处逻辑漂移 | 中 | 公式/类型归一在离线侧完成；内核兜底只做 HIGHLOW += delta，逻辑保持一页可读 |
| CE01 头/尾部元数据与现有装载器解析冲突 | 中 | 元数据尾部追加、 magic 校验；无表旧镜像走原路径 |

| 非抢占假设下补丁循环过长影响调度时延 | 低 | 条目数阈值；补丁在装载一次性完成，不在 syscall 热路径 |
| 与并行批次 B 代码改动冲突 | 低 | 本文档只新增 docs 文件；实现期再按当时 task.c 现状核对行号 |

# CSO1 动态链接库（v2.47）

## 结论

CatOS 现在支持**运行时动态链接**：CE 程序可以在运行时用 `dlopen()` 装载
一个不在自身镜像中的共享库，用 `dlsym()` 按名字解析导出函数并直接调用，
最后用 `dlclose()` 卸载。这是真正的新代码装载，不是构建期合并。

对应的三个 syscall 以 append-only 方式追加到 `catos_api_t` 槽位 66/67/68，
老的 `.ce` 二进制完全不受影响（它们只会看到不存在的尾部槽位）。

## 设计取舍

完整 PE 动态链接器（导入表/导出表/GOT/PLT/共享页/引用计数）在当前内核模型
下成本过高，见 `docs/pe-dynamic-linking-design.md`。本实现采用的是介于
"离线静态重定位" 与 "完整 ld.so" 之间的轻量方案：

- **固定基址**：每个 CSO1 库在链接时就绑定到 `0x2700000..0x2800000` 内的
  一个页对齐地址，装载地址 == 链接地址，因此**不需要重定位引擎**。
- **平坦映射**：库被映射进调用任务自己的 PDE 9 页表，每个任务持有独立
  的物理帧副本；跨任务共享物理页属于后续路线 2 的增强项。
- **同一套 syscall ABI**：库通过装载时注入的 `__ce_api` 指针调用系统服务，
  和普通 CE 程序完全一样，不引入额外的下层 API。

## CSO1 文件格式

```
偏移  长度  字段
0     4     magic "CSO1"
4     4     version = 1
8     4     load base VA（页对齐，落在库区内）
12    4     image_size（代码+数据原始字节）
16    4     bss_size
20    4     api_offset（4 字节 API 指针槽偏移；0xFFFFFFFF = 无）
24    4     export_off（导出表在文件中的偏移）
28    4     export_cnt
...   8*cnt 导出项 { name_off, func_off }
...   N     NUL 分隔的导出名
...   image_size 原始镜像
```

## 使用方式

构建共享库（每个库使用不同的页对齐基址）：

```sh
export PATH=/c/msys64/mingw32/bin:$PATH
cd kernel_v25
sh extapp/build_so.sh libmath.c bin 0x2700000 \
    add=lib_add,sub=lib_sub,mul=lib_mul,gcd=lib_gcd,version=lib_version,hello=lib_hello
```

CE 程序侧：

```c
#include "ce_abi.h"
int h = api->dlopen("/bin/libmath.so");
int (*add)(int,int) = (int(*)(int,int))api->dlsym(h, "add");
int r = add(7, 5);              /* 12 */
api->dlclose(h);
```

built-in 安装器会把 `/bin/libmath.so` 随内核镜像写入 FAT32 卷；
`build/apps.list` 中的 `dltest` 是完整的演示客户端。

## 实机验证

`tests/dl_probe.py`（QEMU 实机，文本模式）：

- `dlopen` 返回 handle 1，六个导出全部解析成功；
- 库函数通过注入的 `__ce_api` 回调内核并成功输出；
- `add/sub/mul/gcd` 结果分别为 12/2/35/12；
- 未知符号与非法 handle 均安全返回 NULL（无崩溃）；
- `dlclose` 返回 0，连续两次运行 dltest 都 PASS（无模块槽泄漏）。

回归：`tests/qemu_regress.py` 12/12（含 mmaptest / hello-elf），
`tests/v245_4gb_probe.py` 在 3840 MiB 下通过，
`tests/btop_probe.py` 通过。

## 限制

- 库镜像按任务独立复制，不共享物理页；
- 库内全局变量若被多个任务同时改写，彼此隔离（因为是各自副本），但
  内存占用会随任务数增长；
- 固定基址要求同一程序装载的多个库地址互不重叠；
- 不支持运行时卸载依赖闭包（只有显式 `dlclose`）；
- 这仍是 CSO1 自有格式，不等同于 Windows DLL / Linux `.so` 的 PE/ELF
  导入表语义；后者属于 `pe-dynamic-linking-design.md` 中的远期路线。

# CatOS 包管理器与仓库链路设计（P4）

## 1. 现状（P4 已实现的本地包路线）

CatOS 客户机在 QEMU 下以 `-net none` 启动，没有可用的网络栈链路，因此 P4
落地的是**本地包仓库**：包容器随内核镜像嵌入，开机播种到 FAT32 卷的
`/pkg/` 目录，`pkg` 命令在本地完成安装/卸载/查询。

```
内核镜像 (catos.iso)
  └─ gen_builtin.py 嵌入
       ├─ /bin/<builtin>.ce        内置应用（apps.list）
       └─ /pkg/<pkg>.catpkg        打包应用（pkg.list，P4 新增）
            └─ PKGS.TXT 索引       name|version|desc|file
```

### 1.1 `.catpkg` 容器格式（宿主侧 `tools/mkpkg.py` 生成）

> v2.68 更新：格式从 `CPKG01` 升级为带 RSA-512 签名的 `CPKG02`。
> 下面以当前代码为准（`tools/mkpkg.py` + `shell.c:pkg_verify`）。

定长 204 字节头 + 原始 CE01 镜像负载，小端序 ASCII 字段，签名 64 字节大端：

| 偏移 | 长度 | 字段 | 说明 |
|------|------|------|------|
| 0    | 8    | magic | `CPKG02\0\0` |
| 8    | 16   | name  | 包名（索引键） |
| 24   | 16   | version | 版本字符串 |
| 40   | 16   | cmd   | 安装后的命令名 → `/bin/<cmd>.ce` |
| 56   | 80   | desc  | 一行描述 |
| 136  | 4    | payload_len | 负载字节数（uint32 LE） |
| 140  | 64   | signature | RSA-512 签名（大端）：`pow(0x01<<56 \| FNV1a64(header\|payload), d, n)` |
| 204  | …    | payload | 原始 `.ce` 镜像（含 CE01 头） |

私钥 `tools/pkg_devkey.txt` 只在宿主侧，内核仅嵌公钥模数 `PKG_PUB_N`；
`pkg install` 用 `pow(sig, 65537, n)` 验签，失败即拒绝安装。旧 `CPKG01`
无签名容器不再被接受。容器格式与 CE01 解耦：未来更换负载格式（ELF/压缩）
只需扩展头部，安装器按 magic 分派。

### 1.2 客户机命令

| 命令 | 行为 |
|------|------|
| `pkg list` | 列出索引中全部包及状态（installed / available） |
| `pkg info <name>` | 显示版本、描述、负载文件、安装状态 |
| `pkg install <name>` | 校验容器 → 解包到 `/bin/<cmd>.ce`，注册为可执行命令 |
| `pkg remove <name>` | 删除 `/bin/<cmd>.ce`（保留 `/pkg/` 仓库副本） |

索引文件 `/pkg/PKGS.TXT` 为简单行式：`name|version|desc|file`。

## 2. 未来：从 Linux 发行版仓库交叉构建 CE 包

> 本节为目标链路设计，P4 不要求全部实现。当前宿主侧只有 `mkpkg.py`
> 打包器与本地索引；联网拉包依赖内核已在位的 e1000 驱动与
> `net_send`/`net_recv` 接口（见 `docs/TODO-2026-11-12-VMware反馈轮.md`
> §四），作为后续扩展点保留。

### 2.1 仓库布局（构建宿主侧）

```
catos-repo/
  dists/
    <catos-release>/
      binary-i386/
        Packages.tar.zst        # 元数据索引（名称/版本/依赖/描述/校验和）
        *.catpkg                # 包容器（格式见 §1.1）
      Release                   # 仓库级签名（时间戳、Packages 校验和）
  pool/
    <upstream-src>.tar.xz
```

- `binary-i386/Packages`：每行一个包，字段对齐 `pkg_meta_t`：
  `name|version|description|cmd|dependencies|sha256`。
- `Release`：仓库清单的 detached 签名（GPG/Ed25519），含 Packages
  文件的 SHA-256 与时间戳，防篡改与回滚。

### 2.2 交叉工具链

| 环节 | 选型 | 说明 |
|------|------|------|
| 编译器 | 现有 freestanding i386 工具链（`gcc -m32 -ffreestanding`） | 与 `extapp/build_ce.sh` 一致；产出 PE flat 镜像 |
| 链接器 | `ld -m i386pe` + `ce.ld` | 入口 `ce_main` 固定在镜像偏移 0 |
| 打包 | `tools/mkpkg.py` | 包元数据写入定长头，负载为 CE01 镜像 |
| 校验 | SHA-256（P4 占位）→ 签名（后续） | 安装前校验负载完整性 |

上游源码（C 库、工具、游戏）在交叉 sysroot 中编译，剥离调试符号后
封装为 `.catpkg`。CE ABI 是追加式的（`ce_abi.h` 槽位只增不删），旧
二进制在新内核上保持兼容。

### 2.3 包构建流水线（目标态）

1. **取源码**：从上游 tarball / git 检出到 `pool/<src>/`。
2. **交叉配置**：`./configure --host=i386-catos --prefix=/usr`（或等价
   裸 Makefile），链接 CatOS freestanding 运行时桩。
3. **编译**：复用 `extapp/build_ce.sh` 的参数族（`-m32 -ffreestanding
   -fno-pic -fno-stack-protector …`），产出对象文件。
4. **打包**：`mkpkg.py` 写入元数据头 + CE01 负载；生成
   `Packages` 索引条目。
5. **入库**：`.catpkg` 放入 `pool/`，元数据追加到 `Packages`；
   `Release` 对 `Packages` 做签名。
6. **客户机安装**：`pkg install <name>` 拉取 → 校验签名/校验和 →
   解包到 `/bin/`。

### 2.4 联网拉包的扩展点（内核已在位）

- 网卡驱动：e1000（`src/e1000.c`），`net_send`/`net_recv` 接口已在
  CE ABI 表中。
- 传输协议：当前无 HTTP 栈；后续可先实现极简 HTTP/1.0 客户端，
  从仓库镜像拉取 `.catpkg` 与 `Packages` 索引。
- 安全：P4 容器头无签名；目标态在 `Release` 中记录 `Packages` 的
  SHA-256，安装器校验负载哈希；签名验证作为后续增强。

### 2.5 依赖与升级（后续）

- 依赖解析：`Packages` 条目的 `dependencies` 字段；安装时拓扑排序，
  先装依赖再装包。
- 升级：`pkg upgrade <name>` 对比仓库版本与本地版本，备份旧包到
  `/var/backup/`，失败可回滚。
- 回滚：保留上一版本 `.catpkg`，`pkg rollback <name>` 恢复。

## 4. 范例：desktop.catpkg —— 图形桌面作为可装卸扩展（v2.69）

这是包机制最有力的证明：`desktop` 是**整个图形桌面环境**，走普通

/pkg/desktop.catpkg --pkg install--> 验签(RSA-512) --> /bin/desktop.ce
   --裸名 desktop--> 运行纯用户态桌面(窗口/焦点/任务栏全在 CE 侧)
   --pkg remove desktop--> 删除 /bin/desktop.ce --> 回到纯 shell

- `desktop.ce` 只用普通 CE ABI：新增的 mouse_x/y/buttons（槽 66..68）

## 5. 远程仓库（v2.70）：pkg repo / update / fetch

本地仓库之外，`pkg` 现在可以从 HTTP 远程仓库拉包，全程复用同一套 RSA-512
验签——远程来源的包和本地包走完全相同的 `pkg_verify()`，签名不符一律拒装。

```
pkg repo http://10.0.2.2:8125/repo   # 设置/查看远程仓库 base URL（存 hive）
pkg update                           # GET <repo>/PKGS.TXT -> /pkg/PKGS.TXT
pkg fetch NAME                       # 按索引文件名拉 <repo>/<file>，验签后装到 /bin
pkg fetch http://IP[:port]/file.catpkg  # 显式 URL 直拉
```

- **二进制安全传输**：现有 `net_http_get()` 是文本 API（`char*`+NUL 结尾、
  rcv_buf 4096、按 Content-Length 截断），不能承载含 0 字节的 `.catpkg`。
  v2.70 抽公共核 `http_fetch()`，新增 `net_http_download(url, uint8_t*, max)`
  返回精确字节数、不做 NUL 结尾；`tcp.rcv_buf` 扩到 20480 容纳整包。
- **验签零分叉**：本地 install 与远程 fetch 共用抽出的 `pkg_install_payload()`，
  包含 magic/length 校验、`pkg_verify()`、写盘 + ACL。篡改 payload 一字节即拒装。
- **安全边界**：仓库 URL 仅接受 `http://`；私钥不进内核，内核只嵌公钥 N。
  传输本身不加密（公开软件包无需机密性，apt/npm 同理），完整性与来源由签名保证。
- 实机验证：`tests/pkg_remote_v270_probe.py` 7/7 PASS——含宿主 HTTP 服务器可达性
  marker、`pkg update` 拉索引、`pkg fetch` 装远程 desktop 并能运行、篡改包被拒。
- 宿主协议原型：`deliverables/pkg-remote-prototype/pkg_remote_proto.py`（真实包字节级验签）。

# cc.ce —— CatOS 微型 C 编译器（目标一 · 任务 #19）

> 源码：`kernel_v25/extapp/cc.c`（1129 行）
> 产物：`kernel_v25/extapp/bin/cc.ce`（镜像 26,876 B / bss 236,832 B，均在 CE 上限 256 KiB 内）
> 内置安装：`build/gen_builtin.py` 会把 `cc.ce` 嵌入内核 → 盘上 `/bin/cc.ce`

## 用法

    run /bin/cc.ce /SRC/HELLO.C /BIN/OUT.CE

成功后打印 `OK -> <输出路径>`。镜像再由内核 `task_spawn_ce` 以常规 CE 方式加载：
镜像装载到 `0x02000000`，`bss_size` 清零，API 表指针写入头部 `api_offset` 指定的 4 字节槽。

## 支持的语言子集

| 类别 | 支持 |
|---|---|
| 类型 | `int` / `char` / `void`，指针 `*`，一维数组 `[]` |
| 声明 | 全局变量（常量初值、字符串初值）、局部变量、字符串字面量 |
| 函数 | 参数、递归、前向调用、`return` |
| 语句 | 块、`if/else`、`while`、`for`、`break`、`continue` |
| 表达式 | `= += -= *= /=`（右结合）、`?:`、`\|\| && \| ^ & == != < > <= >= << >>`、`+ - * / %`、一元 `- ! ~ * &`、函数调用、下标 |
| API | `api->write("x")` / `api->print_int(n)` 等 48 个槽位均可直接调用 |

**不支持**（编译器会明确报错并给出 token 位置）：`struct` / `union`、`switch` / `case`、`goto`、`typedef`、浮点、多维数组、可变参数、位域、函数指针。

## 代码生成模型

栈式单累加器，表达式结果恒在 `EAX`：

- 二元运算：`push 左` → 求右值 → `pop ecx` → 运算（`ecx`=左，`eax`=右）
- 调用：左到右求值并压栈，再原地反转成 cdecl 的右到左顺序
- 除法/取模：`xchg eax,ecx` 让除数落到 `ecx`，`cdq` + `idiv ecx`
- 局部变量：`ebp` 相对寻址；函数序为 `push ebp / mov ebp,esp / sub esp,frame`

## 镜像布局

```
偏移 0            code（ce_main 位于头部 entry 字段指向处）
偏移 len(code)    data（字符串字面量 + 全局变量）
偏移 len(code)+len(data)   __ce_api 槽（4 字节，内核写入表指针）
```

**槽位放在最后**是有意为之：早期版本把槽放在偏移 4，内核写入表指针时会覆盖
代码第 5 个字节，导致程序一启动就跳到错误地址。

函数调用与数据地址在 `fixup_code()` 里统一回填；由于目标与补丁点同在 code 区，
API 槽的布局偏移在 rel32 计算中相互抵消。

## 构建

    cd kernel_v25/extapp
    sh build_ce.sh cc.c

构建脚本对 CE 程序做了两处关键处理（缺一则 `cc.ce` 无法生成）：

- `--disable-reloc-section`：否则 PE 的 `.reloc` 段落在 `.bss` 之后，`objcopy -O binary`
  会把 851 KiB 的零间隙写进镜像，远超 `CE_MAX_IMAGE`
- `objcopy -R .bss`：`.bss` 由内核按 `bss_size` 清零，不应进入文件

## 验证

    python tests/test_cc.py

宿主侧把 `cc.c` 编译成本机可执行（`tests/host_shim.c` 用真实文件系统实现 `catos_file_*`），
再把产出的 `.ce` 交给 `tests/ce_sim.py` 执行并比对输出。当前 8/8 用例通过：

算术、除法/取模、`for`+`break`、`while`、递归（fib(10)=55）、全局 `char *` 字符串、比较运算。

# GO-DESIGN.md — CatOS `go.ce` 用户态 Go 子集解释器

版本：v1.0（QEMU 实测 PASS）
参照：`extapp/node.c`（JS 子集解释器，CE 程序范本）
构建：`sh extapp/build_ce.sh go.c` → `extapp/bin/go.ce`

---

## 1. 目标
在 CatOS（GNU 工具链自举路径，目标一延续）提供一个**可自举的 Go 运行环境**：
一个跑在 CatOS 用户态的 CE 程序 `go.ce`，能用 Go 语法执行脚本，并能解释一个更小的 Go 子集程序（自举）。

## 2. CE 契约（v2.5，与 node.c/cc.c 完全一致）
- CE01 20B header：magic=`CE01`，`entry=0`（`ce_main` 在 `.text.ce_entry`，链接脚本置首）。
- api 槽在 image 末尾（`api_off+4 == image_size`），由 `build/mkce.py` 写入；48 槽与 `ce_abi.h`/`include/ce.h` 逐槽对齐，**未改任何头文件**。
- 构建产物头 v1.1（`xxd -l 20 bin/go.ce`）：
  ```
  4345 3031  magic="CE01"
  0000 0000  entry=0
  c092 0200  bss_size=0x000292c0 (168640)
  2053 0000  api_offset=0x00005320
  2453 0000  image_size=0x00005324 (21284)
  ```
  校验：`0x5320 + 4 = 0x5324 == image_size`。✓

## 3. 子集规格（v1.0）
分层：**词法(lexer) → 语法(parser, AST) → 求值(eval)**，与 node.c 同构。

| 类别 | 支持 |
|---|---|
| 注释 | `// 行` 与 `/* 块 */` |
| 字面量 | 十进制 int、字符串 `"a\nb"`（`\n \t \" \\ \0`）、`true/false`、字符 `'A'`（→ int，支持 `\n \t \r \0`） |
| 声明 | `var x = e`（可选类型名被跳过）；短变量 `x := e` |
| 赋值 | `x = e`、`a[i] = e` |
| 算术 | `+ - * / %`（32 位截断，`/` 向零取整）；字符串 `+` = 拼接 |
| 比较 | `== != < <= > >=`（字符串比内容） |
| 逻辑 | `&& || !` |
| 控制 | `if/else`、三段子句 `for i:=0;i<n;i=i+1{}`、while 式 `for cond{}`、`break/continue`、`return e` |
| 函数 | `func name(p1,p2){...}` 递归、闭包定义作用域 |
| 数组 | `[1,2,3]` 混合值数组；下标读写；`len(a)` |
| 报错 | 词法/语法错含**源行号**（`go: syntax error at line N`） |
| 容量 | 源缓冲 `g_filebuf[20480]`（≥8KB）；解释器 arena 经 `api->alloc` 从内核堆取 192KB（fallback 静态 64KB） |

内建函数（注册于全局作用域）：
`print(...)`（空格分隔+换行）、`len(s|a)`、`readfile(path)->string`、`argv(n)->string`、`atoi(s)`、`chr(n)->string`、`sub(s,start,n)`、`string(n)`、`append(arr,v)`。
字符串下标 `s[i]` → 字节 int。

脚本选择（首个命中）：`argv[1]` → `/BIN/DEMO.GO` → 内嵌 demo。

## 4. 自举定义与验收标准
**自举定义**：用 Go 子集本身写一个迷你解释器 `MINI_GO.GO`，它在 `go.ce` 下运行，并读取+解释另一个更小的 Go 子集程序 `MINI_IN.GO`（仅支持 `x = 数字`、`x = y op z`、`print x`，26 个字母寄存器）。

- `MINI_GO.GO` 用内建 `readfile(argv(2))` 读入目标源码，空白分词成 string 数组，逐 token 解释赋值/print。
- 验收：`run /bin/go.ce /BIN/MINI_GO.GO /BIN/MINI_IN.GO` 的输出**逐字节等于宿主预期**。
- `MINI_IN.GO`：
  ```
  a = 3
  b = 4
  c = a + b
  print c
  ```
  宿主预期输出：`7`。QEMU 实测屏显确认为 `7`（截图 `cc_shots/go_r6_selfhost.png`）。✓

## 6. 迭代清单（含双审 go-review.md FIND 修复状态）
### 已修复（v1.1，双审 P1 闭环，QEMU go_fix 回归 PASS）
- **FIND-G1（P1）语法错误行号不定位**：`Tok` 增加 `line` 字段，lex 时记录 token 起始行；`perr()` 取当前 token 行号（不再因 lex 一次扫完全文而冻结在文末）；未闭合 `(`/`(` call 缺 `)` 时改报开括号所在行。实测 SYN.GO（第 3 行缺 `)`）报 `line 3`。
- **FIND-G2（P1）字符串 `+` 拼接 199 字节硬截断**：删掉栈上 `tmp[200]`，改用 arena 按 `v_disp_len(l)+v_disp_len(r)` 动态分配拼接缓冲；数字/布尔操作数内联渲染。实测拼接 250 字符 `len=250`（原 199），`"n="+42 → "n=42"`。

### 未修（P2，列入后续迭代）
- FIND-G3 无 Go 递归栈深上限（建议 g_call_depth>200 rerr）。
- FIND-G4 非法字符被词法 default 静默吞成运行时错（建议 default 分支 perr）。
- FIND-G5 readfile 请求 20479 但内核 file_read 单次上限 16384（>16KB 脚本需分块读取；当前脚本 <3KB）。
- FIND-G6 arena 扩容 `s->v`/`a->v` 未判空。
- FIND-G7 字符串字面量 >1023 静默截断、未闭合引号不报错。
- FIND-G8 顶层 break/continue/return 静默停跑不报错。
- FIND-G9 for init `:=` 变量泄漏外层作用域（非 Go 循环作用域，无害）。
- FIND-G10 数字字面量溢出无检测（int32 UB）。

### 远期
- map/结构体、`range`、多行返回值、`fmt.Println` 包路径；真编译为 CE 产物；MINI_GO.GO 扩到完整表达式优先级与注释/字符串字面量。

## A. 词法 / 语法层

| 检查点 | 结论 | 证据 |
|---|---|---|
| 标识符 intern（NUL 结尾副本） | ✅ | lex 期 T_ID.sp 指向源缓冲（非 NUL），但 `p_primary` go.c:443 与 var/func/形参处（:504/:520/:526/:533）均经 `a_strn(sp,len)` 拷入 arena 且 `sncpy` 后补 NUL（:50-53）；`scope_find` 用 `scmp`（strcmp）依赖的正是这些 NUL 副本，自洽 |
| 字符串转义 `\n \t \" \\ \0` | ✅ | `lex_string` go.c:218-225 switch 命中 n/t/"/\\/0，共 5 种，与 GO-DESIGN §3 表所列 5 种一致（未宣称 `\r` 入串） |
| 字符字面量 `'A'`/`\n \t \r \0` | ✅ | `lex_char` go.c:240-241 支持 n/t/r/0；MINI_GO.GO:23 用 `c == '\r'` 依赖此点，宿主跑通 |
| `!` 一元 vs `!=` 二元 | ✅ | lex go.c:293-296：下一字符为 `=`→OP_NE，否则→`!`；`p_unary` go.c:409 仅认 `!`，无歧义 |
| `:=` 短变量 | ✅ | lex go.c:310 把 `:=`/`:` 都映射为 `:` op；`p_stmt` go.c:615-620 用 `tok_is_op(':')` 判 shortv，`=` 走普通赋值 |
| 比较链 `a < b < c` | ✅ 可接受 | `p_cmp` go.c:377-389 左结合循环解析，宽容但不产出错误 |
| 优先级（precedence climbing） | ✅ | or→and→cmp→add→mul→unary→postfix→primary（go.c:359-467），TEST.GO `2+3*4=14`、`(2+3)*4=20` 实测正确 |
| **词法/语法错带行号** | ⚠️ **不定位（P1，见 FIND-G1）** | 见下 |

**FIND-G1（P1）——语法错误行号恒为"文件总行数"，不定位错误行。**
- 根因：`lex_run`（go.c:261-316）在解析前**一次性扫完全文**并推进 `g_line`；解析阶段 `perr()`（go.c:344-347）捕获的 `g_line` 已冻结在文末行号。`Tok` 结构（go.c:166-171）**没有 per-token line 字段**。报错处 go.c:1135-1136 输出 `g_errline`（= 文末）或 `g_line`（= 文末）。
- 实测（host）：6 行脚本中第 5 行 `var e = (1 + 2`（缺右括号），报 `syntax error at line 7`；3 行脚本缺 `}`，报 `line 4`。两者都是"行数+1"，与错误实际位置（5、3）无关。
- 影响：GO-DESIGN §3 明示"词法/语法错含源行号（go: syntax error at line N）"——该功能**名不副实**，N 对定位无帮助。不影响验收链（验收脚本无语法错）。
- 一行级修复（交开发子代理）：给 `Tok` 加 `int line` 字段，`lex_add` 时盖当前 `g_line`；`perr()` 改为 `g_errline = cur()->line`（错误发生时当前 token 的行）。

**P2 附记**：非法字符（如 `@`）落入 lex 默认分支 go.c:313 `g_pos++; break;` 被**静默丢弃**，把一个词法错延迟成运行期 `undefined variable`（实测 `var e = @bogus` → "runtime error: undefined variable" 而非 syntax error）。建议 default 分支 `perr`。

## B. 值模型

| 检查点 | 结论 | 证据 |
|---|---|---|
| int 算术 + 除/模零保护 | ✅ | go.c:886-892；`r.num==0` 时 rerr 并返 0（:889/:891），TEST `20/6=3`、`20%6=2` 通过 |

| 值拷贝 vs 引用 | ✅ by design | GVal.op 为数组/函数指针，数组赋值/传参为**浅引用共享**（append 原地长大），MINI_GO 的 `reg[slot]=...` 依赖此语义，实测正确 |

**FIND-G2（P1）——字符串 `+` 拼接在栈上 `tmp[200]` 内硬截断到 199 字节，静默丢数据。**
- 根因：go.c:878-884 字符串拼接分支用 `char tmp[200]`、`k<199` 限制，超出部分直接丢弃，再 `a_str(tmp)`。
- 实测（host）：`for i<250 { s = s + "x" }` 后 `len(s)` = **199**，不是 250。
- 影响：GO-DESIGN §3 把字符串 `+` 宣传为拼接、未声明长度上限。自举 MINI_GO 的分词器 `cur = cur + chr(c)`（MINI_GO.GO:29）逐字符累积——若目标源码出现 >199 字符的无空白 token，`cur` 会被静默截断导致解释结果错。验收脚本 token 均 ≤1 字符，不受影响；但这是**受支持操作的静默错编**类缺陷（与 cc-review 的 P1 同类）。
- 一行级修复（交开发子代理）：删掉 `tmp[200]`，改为 `int k = l.slen + r.slen; char *p = a_alloc(k+1); memcpy 两段; return v_str(p,k);`（arena 已具备动态分配能力）。

## C. 求值器

| 检查点 | 结论 | 证据 |

**P2 附记**：
- **FIND-G3 无递归深度上限**：Go 递归每级都嵌套一层 C `call_user`（go.c:953→:941），无限递归（`func f(){f()}`）会撑爆 C 调用栈——CE 仅 64KiB 用户栈，会缺页杀任务；arena OOM 能挡住内存但挡不住栈深。建议加一个 `g_call_depth` 计数（>200 帧 `rerr`）。验收递归深度 ≤10，安全。
- **FIND-G8 顶层 break/continue/return 静默吞掉**：顶层 `exec_list`（go.c:774）见 `g_flow!=0` 即停跑后续语句，但不报错，也不复位。属脚本编写错误被静默忽略。
- **FIND-G9 for init 的 `:=` 变量泄漏外层作用域**：go.c:816 直接在当前 scope declare（如 `i`），非 Go 的循环作用域；无害但语义略宽。

# CatOS 图形模式能力说明（VGA Mode 13h）

**版本**: v0.3 图形化（stage5）
**日期**: 2026-11-05
**状态**: 已实施 + QEMU 多轮实测通过

---

## 一、一句话定位

CatOS 内核现在带一个**真正的图形模式**：通过 VGA Mode 13h（320x200、256 色、线性帧缓冲），
在文本终端之外提供**像素级绘图 + 位图字体软终端**两条渲染通道，shell 内可随时往返切换。

```
文本模式 (默认开机)  --gfx-->  图形模式 (320x200x256)
        ^                              |
        +--------text------------------+
```

---

## 二、现在能干什么（能力总览）

### 2.1 shell 交互命令

| 命令 | 作用 |
|---|---|
| `gfx` | 切入图形模式，并运行内置演示（渐变带/边框/标题/色块/网格/信息文本） |
| `text` | 切回 80x25 文本模式（字形完整恢复，无竖条纹 bug） |
| `vdiag` | VGA 寄存器诊断：寄存器组、属性调色板、DAC 前 3 色、'A' 字形读回校验 |

### 2.2 像素级绘图 API（C 内核侧）

| API | 功能 |
|---|---|
| `gfx_putpixel(x, y, c)` | 单像素点（链式写帧缓冲，无字节对齐限制） |
| `gfx_fillrect(x, y, w, h, c)` | 实心矩形填充 |
| `gfx_hline / gfx_vline` | 横线 / 竖线 |
| `gfx_rect` | 空心矩形边框 |
| `gfx_drawchar(x, y, ch, fg, bg)` | 8x8 点阵字符（前景/背景色） |
| `gfx_text(x, y, s, fg, bg)` | 字符串文本绘制 |

### 2.3 软终端（40x25 位图终端）

| API | 功能 |
|---|---|
| `gfx_term_init / clear` | 初始化 / 清屏 |
| `gfx_term_putc / write` | 逐字符 / 整串输出 |
| `gfx_term_set_color(fg, bg)` | 前景 / 背景色 |
| 滚动 | 满屏后整屏上移 8 像素（逐行上移 1 像素，模拟平滑滚动） |
| 换行 / 回车 / 制表 | 完整处理，行为与文本终端一致 |

### 2.4 颜色系统

- **DAC 调色板**：0-15 为标准 VGA 色（黑蓝绿青红紫棕灰 + 亮色系），16-255 为灰度渐变
- 通过端口 `0x3C8 / 0x3C9` 写入，全 256 项一次装载
- 图形模式下可对任意像素指定 256 色中的任意索引

### 2.5 模式切换基础设施

- `gfx_mode13h()`：标准 Mode 13h 寄存器序列（MISC/SEQ/CRTC/GC/AC 全套）
- `gfx_text_mode()`：标准 Text 03 序列（含 CRTC 0x11 恢复、seq01 屏幕开关、属性模式恢复）
- `vga_gfx_enable() / vga_gfx_disable()`：shell 命令的桥接入口
- `vga_clear/putc/set_color/set_fg` 全部带图形分支，内核其余子系统无需感知模式

## 一、本包包含的新成就

### 1. 内核图形模式（VGA Mode 13h）
- **320x200x256** 帧缓冲模式，8x8 点阵软终端（40x25 网格）
- shell 新增命令：**`gfx`** 进入图形模式、**`text`** 返回文本模式
- DAC 调色板：0-15 标准 VGA 色 + 16-255 灰度渐变
- 图元：putpixel / fillrect / hline / vline / rect / drawchar / text
- 图形演示：渐变横带 + 白边框 + 标题 + 16 色块 + 信息文本

### 2. 关键 bug 修复：`text` 切回后竖条纹屏（字形缺失）
**根因**（QEMU v8.2.0 `hw/display/vga.c` 源码取证）：
- QEMU 的 VGA 内存窗口映射由 `GC 0x06` 决定：`memory_map_mode = (GR06>>2)&3`
- 文本模式 `GR06=0x0E` → **mode 3（B8000 32KB 窗口）**：
  ```c
  case 3: addr -= 0x18000; if (addr >= 0x8000) return;  /* 静默丢弃 */
  ```
- CPU 向 **0xA0000** 的写入被判定为窗口外地址（addr 下溢），**全部静默丢弃**
- 因此旧版 `vga_reload_font()` 写 0xA0000 字形区完全无效，QEMU 渲染引擎读到 chain4 污染后的垃圾 → 竖条纹
- 图形模式 `GR06=0x05` → mode 1（A0000 64KB 窗口），0xA0000 写有效，故 gfx 正常

**修复**：`vga_reload_font()` 改经 **0xB8000 窗口** + **latched 写**（`GR05=0x00`）：
- 窗口偏移 `a = 32*c + r` → `vram[4*a + plane] = vram[128*c + 4*r + 2]`
- 与 QEMU 渲染读取位置（`font_base = vram + 2 + 128*ch`）**逐字节一致**

**验证**：
- 内核 `vdiag` 命令读回 `'A'` 字模 = `00 00 20 20 50 50 88 88`，与内置 font8x8_basic 完全一致
- QEMU 实测：gfx 图形模式渲染正常 → text 恢复文本正常（无竖条纹）→ 再次 gfx → text 多轮往返稳定
